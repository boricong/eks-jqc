## 시작

Node 24가 필요합니다. 검증 환경은 Node 24.22.0 / npm 11.9.0입니다. 저장소 루트에서 실행합니다.

```sh
npm ci
npm run data:init
npm run dev
```

`data:init`은 첫 실행에만 필요하며 기존 파일을 덮어쓰지 않습니다. 이후에는 `npm run dev`로 다시 시작합니다. Node 버전 관리 도구를 사용한다면 `.nvmrc`의 24를 선택합니다.

- 프런트엔드: [http://127.0.0.1:5186](http://127.0.0.1:5186)
- API: `http://127.0.0.1:5187/api` — 개발 중 `/api`는 Vite가 전달합니다.
- 정적 빌드 실행: `npm run build` 후 `npm start`. 이 경우 [http://127.0.0.1:5187](http://127.0.0.1:5187)에서 앱과 API를 함께 제공합니다.

상단에서 가상 계정을 선택합니다. 서버는 HttpOnly·SameSite 쿠키로 세션을 구분하고 역할·본인·담당 관계를 검사합니다. 계정 선택은 검증 환경의 전환 기능이며 비밀번호 인증은 포함하지 않습니다. 서버는 `127.0.0.1`에만 바인딩됩니다. 세션은 8시간이며 서버를 다시 시작하면 계정을 다시 선택합니다.

## 저장·백업·복구

- 런타임: `data/runtime/state.json` (`schemaVersion: 1`). 응시, 수료, 인증, 근거, 변경 이력, 비교 기록, 중복 요청 정보가 함께 저장됩니다.
- 초기 샘플: `server/src/seed-source.json`과 `seed.ts`. 정답은 서버에서만 취급하며 학습자 DTO와 프런트엔드 정적 파일에는 포함하지 않습니다.
- 자동 백업: `data/backups/state/state-<revision>.json`, 변경 직전 상태 최대 20개. 수동 백업과 복구 전 파일은 자동 삭제하지 않습니다.
- 파일 검사·처리·백업·원자적 저장은 하나의 쓰기 대기열에서 실행합니다. 같은 저장소를 사용하는 두 서버는 실행할 수 없습니다.
- `EKS_DATA_FILE`로 다른 저장소의 절대 경로를 지정할 수 있습니다. 초기화·실행·백업·복구에 같은 값을 적용해야 합니다. 백업은 해당 파일 디렉터리의 `../backups/<파일명>/`에 생성됩니다.

**서버를 종료한 뒤** 수동 백업·복구를 실행합니다.

```sh
npm run data:backup
npm run data:restore -- "data/backups/state/manual-<생성시각>.json"
```

첫 명령이 출력한 실제 백업 경로를 두 번째 명령에 넣습니다. 복구는 JSON 형식과 참조·채점·근거의 무결성을 검사하고, 현재 파일을 `before-restore-*.json`으로 보관한 뒤 교체합니다. 손상된 저장소는 시작을 중단하며 자동 초기화하지 않습니다.

비정상 종료로 잠금만 남았다면 `npm run data:unlock`을 실행합니다. 잠금에 기록된 프로세스가 종료된 경우에만 해제합니다. 실행 중인 서버를 강제로 해제하는 명령은 없습니다. 런타임·백업·잠금 파일은 Git에 포함하지 않습니다.

## 검증

```sh
npm run build
npm test
npm exec -w frontend -- playwright install chromium
npm run test:e2e
```

서버 시험은 Node 테스트 러너와 Fastify `inject`를 사용합니다. Playwright는 5286/5287의 테스트 서버를 자동 기동하고 테스트마다 임시 저장소를 사용하므로 개발 데이터는 변경하지 않습니다. 두 테스트 포트는 비어 있어야 합니다. 기본 브라우저는 Playwright Chromium이며 필요할 때 `PLAYWRIGHT_CHROMIUM_EXECUTABLE`로 경로를 지정합니다.

화면 캡처와 실패 추적 파일은 `frontend/test-results/`에 저장합니다. 일반 시험은 `docs/preview/`의 기존 화면 자료를 덮어쓰지 않습니다.

## 구현 범위

응시 자동 저장·재개, 서버 채점, 부분 통과 유지, FT 배정 검사, 합격 응시를 연결한 수료·자동 인증, 기준 버전 고정, 변경 이력, 공지, 학습자료 URL, 필기/Case 분류를 지원합니다. 관리의 `기준 검증`에서는 과정별 평가 회차와 별도의 실제 수행 근거를 비교하고, 확정 후 정정은 원본을 보존한 새 기록으로 남깁니다.

Recipe Management는 미완성 초안으로 보존합니다. 기능 시험은 별도의 `평가 흐름 체험` 가상 자격을 사용합니다. 실제 문항·실기 기준·독립 수행 근거·참여자·파일럿 성공 조건은 준비가 필요하며, 시스템 시험 통과가 평가 기준의 타당성 입증을 의미하지 않습니다.
