# 주관식 평가 — 답변 수집 전용

2026-10-26 · 업무22 · 조직4 · 기본정보 JSON12

## 운영 정책

Auditee의 공통·특화인증Set에 문제 본문만 있는 주관식 문항을 설정한다. Auditor는 기존 본인 학습 확인 방식을 유지한다. 정답·배점·합격 기준·채점·피드백·재응시는 제공하지 않는다. 주관식의 설정·작성·제출 상태는 준비 상태, 지식→상황 대응의 필수 평가 순서, 진행률·수료·인증·갱신 판정에 사용하지 않는다. 기존 필수 평가 기준 없이 주관식만으로 운영할 수는 없다.

문제와 답변은 문항당20,000자, 문항은 최대500개다. 문항 편집은 추가·삭제·순서 변경을 지원하고 사용 해제 시 내용은 보존한다. 미완성 저장을 허용하되 활성화된 빈 목록/빈 문제는 보완 안내와 함께 답변 시작만 막는다. 공통 원본 수정은 기존 팀 사본이나 배정에 소급하지 않는다. 팀 사본의 수정·새 버전·공통 분류·팀 수정 표시는 기존 정책을 따른다.

학습자는 필수 평가 통과 여부와 무관하게 주관식을 시작하고 여러 줄의 일반 텍스트를 자동 임시 저장한다. 공백을 제외한 답변이 모든 문항에 있어야 전체 답변 확인 후 최종 제출할 수 있다. 수강별 기록은 하나이며 제출 취소/수정은 없다. 미작성·작성 중·답변 제출 완료·수료로 작성 종료 상태를 표시한다. 인증Set 수료가 먼저 저장되면 미제출 초안도 읽기 전용으로 보존한다. 마지막 필수 평가 제출 확인에서 미제출 주관식을 안내하지만 필수 평가 제출을 막지 않는다.

## 데이터·조회 범위

- 공통 내용: `subjectiveEnabled`, `subjectiveQuestions: {id,prompt}[]`. 공통 복사 시 문항 ID도 새로 부여한다. 비활성·빈 문항은 기존 내용 해시와 같게 정규화한다.
- `subjectiveResponses`: 수강/인증Set/학습자 ID, revision, 시작 시점 문항 스냅샷, 문항 ID별 문자열 답변, draft/submitted 상태, 작성/수정/제출 시각. 자동 평가의 종류·숫자 답안·완료 근거와 분리한다.
- 본인은 자신의 초안과 제출 기록을 읽는다. 기존 결과 조회 권한이 있는 관리자는 조직 범위 내 **제출 답변만** 읽는다. 운영자도 다른 사람의 초안은 읽지 못하며 세부 관리자에게 새 결과 조회 권한을 부여하지 않는다.
- 워크스페이스에는 비공개 초안 본문을 넣지 않는다. 생성·제출 감사에는 참조 ID와 문항 개수만 남기며 답변 본문을 남기지 않는다. 기본정보 JSON에는 문항 설정만 포함하고 답변은 제외한다.

## 공개 API

모든 쓰기는 기존 세션·요청 키·내용 해시·영수증과 직렬 쓰기 대기열을 사용한다. 읽기는 기록을 생성하거나 수정하지 않는다.

| API                                             | 입력                 | 출력 및 보류 조건                                                                       |
| ----------------------------------------------- | -------------------- | --------------------------------------------------------------------------------------- |
| `GET /api/enrollments/:id/subjective-response`  | 본인 수강 ID         | `{response,canWrite,reason,status}`. 미시작이면 response는 null. 다른 사람은403         |
| `POST /api/enrollments/:id/subjective-response` | 빈 객체              | `{id,revision}`. 이미 시작했으면 같은 기록 반환. 미설정/미완성·수료·Hold·제외 상태는409 |
| `PUT /api/subjective-responses/:id/draft`       | `{revision,answers}` | 새 revision. 모르는 문항·문자열 외 답변·20,000자 초과·채점 필드는422                    |
| `POST /api/subjective-responses/:id/submit`     | `{revision}`         | 저장된 전체 답변을 제출하고 새 revision. 빈 답변은422 `SUBJECTIVE_ANSWERS_REQUIRED`     |
| `GET /api/subjective-responses/:id`             | 기록 ID              | 본인 또는 기존 권한 내 제출 기록. 다른 초안/조직은403                                   |

쓰기 대기열에서 최신 본인 배정·역할·활성 조직·Hold/제외·수료·revision을 다시 검사한다. 수정 충돌은409 `REVISION_CONFLICT`, 작성 종료는409 `SUBJECTIVE_WRITE_CLOSED`로 보류한다. 성공 영수증은 동일 요청 키/본문의 응답 유실 재시도를 복구한다. 수료와 제출은 먼저 저장된 작업을 따른다. 저장 실패 시 부분 답변·중복 제출 감사를 남기지 않는다. 브라우저는 오류 시 입력을 보존하고 재시도·서버 답변 재확인·이동 전 미저장 확인을 제공한다.

기존 `/.../subjective` 화면과 과거 FT·주관식 채점 API는 계속 종료 상태다. 새 학습 화면은 `/qualifications/:id/courses/:courseId/subjective-response`다. 인증Set 개별/공통 저장에서 새 문항 필드만 명시적으로 허용한다. 대량 텍스트를 위해 해당 기준 저장·미리보기·주관식 초안·기본정보 JSON의 요청/파일 한도는64MiB이며 각 문항 제한은 별도로 검사한다.

## 이관·보존·복구

일반 시작은 업무21을 자동으로 바꾸지 않는다. 명시 이관은 기존 인증Set·공통 원본에 비활성/빈 문항, 업무 상태에 빈 답변 목록을 추가하고 업무 revision과 이관 감사만 증가시킨다. 조직4와 기존 계획·배정·응시·학습·수료·인증·보존 스냅샷·폐지 기록·공통 기준 해시는 그대로 유지한다. 재실행은 무변경이다.

1. 검증 후 서버를 종료하고 최신 업무·조직·maintenance 세 파일 및 업무21 호환 소스를 백업한다. 경로·환경변수·revision·SHA256을 기록한다.
2. 같은 `EKS_DATA_FILE`·`EKS_ORGANIZATIONS_FILE`로 `npm run data:migrate-subjective -- --dry-run`을 실행한다.
3. `npm run data:migrate-subjective -- --apply --expected-revision=N --expected-sha256=STATE_SHA256 --organization-sha256=ORG_SHA256`으로 적용한다.
4. 허용된 필드/감사 외 기존 업무 전부, 조직 바이트, 공통 기준 해시를 대조한다. maintenance는 generation만 바뀐다. 반복 이관의 무변경도 확인한다.
5. 같은 설정으로 재시작하고 health·실제 화면을 조회만 확인한다. 조회 전후 세 파일 해시를 비교한다.

실패 시 원본을 보존/복구한다. 운영 복구는 서버 종료 후 업무21 호환 코드·해당 잠금 파일 기준 의존성과 백업한 세 원본을 함께 사용한다. JSON1~11은 기존 형식/체크섬/건수/참조 검증 후 비활성/빈 문항으로 호환 변환하며 새 주관식 데이터를 구형 파일 형식으로 위장하면 거부한다. 기준 보존 초기화는 문항을 남기고 답변과 관련 진행 영수증을 정리한다. 답변은 인증Set 참조/삭제 영향 검사와 초기화 개수에 포함한다.
