# 객관식 재인증 운영·개발 계약

업무 스키마28·조직 스키마4. Auditee 재인증은 실제 객관식 평가의 합격 근거로 기존 인증을 갱신한다. Auditor 본인 교육·인증기준 확인 갱신은 유지한다. 설정 JSON·Excel 기능은 다시 제공하지 않는다.

## 기준 준비

1. 시스템 기본자격에서 용도를 `재인증 · 객관식 전용`으로 지정한다. 시스템 전체에서 하나만 만들 수 있으며 Auditee만 허용한다. 팀 등록 이력 이후에는 용도를 변경할 수 없다.
2. 각 팀이 같은 풀 기본자격을 등록하고 인증Set을 구성한다. 공통 사본 또는 특화 인증Set 한 개를 연결한다. 최초 설정은 v1·Hold로 저장하고 준비가 끝나면 운영 상태를 Active로 전환한다.
3. Active 재인증 자격은 팀마다 한 계보만 허용한다. 지식 평가만 포함하고 상황 대응 문항, 주관식 활성화·보존 문항이 없어야 한다. 문항·배점·합격 기준은 기존 지식 평가 계약을 사용한다. 자료는 참고용이며 학습 확인은 선행 조건이 아니다.
4. 미완성 인증Set과 Hold 자격을 저장할 수 있다. 미완성·복수 인증Set·잘못된 평가 구성은 Active 전환을 막는다. 공통 또는 팀 인증Set 개정이 객관식 단독 조건에 맞지 않으면 연결 갱신을 보류하고 기존 연결을 유지한다.

재인증 자격 자체의 인증기간은 사용하지 않으며 편집 화면에서 숨긴다. 조직 필요자격·일반 계획 후보·일반 취득 진행 집계에 포함하지 않는다. 실제 재인증 원본·팀 자격·문항은 자동 생성하지 않는다.

## 학습자 흐름

`보유 자격 → 재인증 → 대상 선택 → 기존/다음 만료일 확인 → 객관식 평가 → 대상별 갱신 결과`

- 현재 팀에서 취득한 기간제 Auditee 인증만 선택한다. 기존 만료 전 갱신 시작 기간·효력·팀 기준 준비 조건을 유지한다. 인증서에서 들어오면 해당 인증을 미리 선택한다.
- 사용자·팀별 미합격 진행 회차는 하나다. 대상·인증 기간·각 대상의 갱신 정책과 재인증 평가 기준은 시작할 때 고정한다. 대상 추가나 다른 미래 기간에 합격 근거를 재사용하지 않는다.
- 새 계획·일정은 만들지 않는다. 별도 재인증 배정·수강으로 기존 답안 임시 저장·동시 편집·최종 제출·불합격 재응시 기능을 사용한다.
- 합격하면 평가·수료 근거를 보존한다. 별도의 재인증 자격 인증은 발급하지 않는다. 원래 인증의 ID·최초 발급일·평가·수료 근거를 유지하고 새 유효기간만 추가한다.
- 각 대상은 시작 당시 원래 자격의 기간 정책으로 기존 만료일부터 연장한다. 개인 인증 Hold, 원래 기준 Hold/삭제/변경, 제외, 만료 등은 대상별로 보류한다. 다른 정상 대상은 갱신한다. 모든 대상이 Hold라도 만료 전 평가 합격 근거는 보존할 수 있다.
- 합격한 회차에서 `보류 대상 다시 적용`을 실행하면 원래 대상만 재검사한다. 각 대상의 원래 만료일을 지난 뒤에는 갱신할 수 없다. 만료 후에는 기존 재취득 절차를 사용한다.
- `회차 종료`는 아직 처리하지 않은 대상만 종료한다. 답안·점수·완료된 갱신은 보존한다. 이후 새 회차를 만들 수 있다.
- 인원 Hold, 현재 팀/역할 변경, 재인증 기준 Hold/삭제는 새 응시·답안 저장·제출·적용을 차단한다. 입력 보존은 기존 평가 편집 계약을 사용한다.

## API·검토 계약

| API                                   | 입력                                                                                          | 출력·보류                                                                              |
| ------------------------------------- | --------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------- |
| `GET /api/me/renewal-candidates`      | 본인 세션                                                                                     | 업무·조직 revision, 운영 재인증 자격 revision, 후보·불가 사유·기존 회차. 쓰기 없음     |
| `POST /api/renewal-batches/preview`   | stateRevision, organizationRevision, qualificationId, qualificationRevision, certificationIds | 선택 대상의 이전/다음 만료일. 선택 없음/중복422, 타인403, 변경/준비 부족409. 쓰기 없음 |
| `POST /api/renewal-batches`           | 미리보기와 같은 입력, Idempotency-Key                                                         | 회차·배정·단일 수강·대상별 renewal 원자 생성. 최신 권한/조직/기준/중복 재검사          |
| `GET /api/renewal-batches/:id`        | 본인 세션                                                                                     | 평가 링크·진행/합격·점수·대상별 결과/사유. 쓰기 없음                                   |
| `POST /api/renewal-batches/:id/apply` | 회차 revision, Idempotency-Key                                                                | 합격 근거로 보류 대상을 재검사. 갱신 가능한 대상만 처리. 잘못된 회차/충돌409           |
| `POST /api/renewal-batches/:id/close` | 회차 revision, Idempotency-Key                                                                | 미처리 대상 종료. 과거 평가·성공 갱신 유지                                             |

평가 API는 기존 경로를 사용한다. 모든 변경은 기존 저장 대기열과 영수증을 사용한다. 응답 유실 재시도는 같은 요청 키·본문으로 실행한다. 저장 실패 시 평가 합격·기간 추가도 함께 롤백된다. 일반 평가의 자동 발급 분기는 `assignment.renewalBatchId`를 확인해 재인증 적용으로 전환한다. 서버는 실제 객관식 통과 응시와 동일 수강의 수료 근거를 검증한다.

Auditee의 이전 `POST /api/certifications/:id/renewals`, `POST /api/renewals/:id/complete`는 인증·대상 접근 권한 확인 후 영수증 조회 전에 `410 FEATURE_REMOVED`를 반환한다. Auditor의 기존 확인 갱신만 계속 허용한다. 관리자 결과 조회는 기존 평가·수료 권한 범위를 유지한다.

## 저장·보존

- 기본자격·팀 자격: `purpose: acquisition | renewal`. 구형 일반 취득은 acquisition으로 명시 이관한다. 일반 용도는 기존 기준 해시에서 생략해 과거 frozenCriteria가 유지된다.
- `State.renewalBatches`: 학습자·팀·재인증 자격·배정·revision·상태·합격 응시/수료 연결·시각.
- `Assignment.renewalBatchId`: 재인증 평가 배정 구분. 일반 취득 집계와 신규 자격 인증에서 제외한다.
- `Renewal.batchId`, `method: objective_assessment`: 각 원래 인증·기간·시작 당시 원래 자격 기준/기간 정책을 보존한다.
- 기존 완료된 MVP 갱신·Auditor 갱신과 과거 기록은 유지한다. 미완료 Auditee MVP 갱신만 명시 이관 시 종료하며 전후 원문을 감사에 보존한다.

## 명시 이관·복구

일반 서버 시작은 업무27을 자동 변환하지 않는다.

1. 서버를 정상 종료한다. 업무 JSON, 조직 JSON, 업무 JSON에 대응하는 maintenance JSON, 업무27 호환 소스를 별도 백업한다. revision과 SHA256을 기록한다.
2. 같은 `EKS_DATA_FILE`·조직 설정으로 `npm run data:migrate-objective-renewals -- --dry-run`을 실행한다.
3. `npm run data:migrate-objective-renewals -- --apply --expected-revision=N --expected-sha256=STATE_HASH --organization-sha256=ORG_HASH`로 적용한다.
4. 업무28·조직4를 확인하고 목적 필드·빈 회차 목록·미완료 Auditee MVP 종료·revision·감사 외의 기록이 동일한지 대조한다. 재이관은 무변경이어야 한다.
5. 기존 환경·포트로 재시작하고 읽기 전용으로 확인한다. 기본자격·문항의 실제 운영 설정은 별도 수행한다.

실패 시 원본을 보존한다. 복구는 서버 종료 후 백업한 세 데이터 파일과 업무27 호환 소스를 함께 사용한다. 일부 파일만 되돌리지 않는다.

## 검증

실제 API 테스트로 단일 평가의 복수 기간 갱신·별도 인증 미발급·부분 Hold 보류/재적용·전부 Hold 합격 보존·만료 거부·다른 사용자 접근·용도 잠금·원본 중복·시작/합격 저장 실패 원자성·동시 요청/응답 유실·기준 변경·짧은 기간·이관 해시와 재실행을 검증한다. 기존 Auditor 확인 갱신·일반 취득·주관식·공통 버전 회귀를 함께 실행한다. 브라우저는 실제 답안 저장/새로고침/제출/결과와 1920·1440·768·390px 화면을 확인한다.
