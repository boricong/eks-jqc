# 문서 등록과 Markdown 표시

헤더의 독립 메뉴 **문서 조회**에서 로그인한 모든 사용자가 등록된 Markdown을 읽는다. 시스템 운영 하위 메뉴와 사이드바는 표시하지 않는다. 목록은 `/documents`, 상세는 `/documents/:id`다. 기존 `/system/documents/:id?` 주소는 검색 조건과 앵커를 보존해 새 주소로 이동한다.

## 문서 등록

1. UTF-8 Markdown 파일을 `docs/` 또는 그 하위 폴더에 추가한다. 파일당 최대 2MiB다.
2. `docs/document-catalog.json` 배열에 아래 형식으로 등록한다.

   ```json
   {
     "id": "operation-guide",
     "title": "운영 안내",
     "description": "운영자가 확인할 절차와 참고 자료입니다.",
     "updatedOn": "2026-10-25",
     "sourcePath": "guides/operation-guide.md"
   }
   ```

3. `npm run documents:check:git`로 목록·파일과 Git 추적 여부를 검증하고, 목록과 원문을 함께 커밋·푸시한다. `npm run documents:check`는 `.git` 없는 배포 폴더에서도 목록·파일을 검사한다. 루트 빌드에도 문서 검증이 포함된다.
4. 코드와 문서 파일을 함께 배포한다. 정적 프런트 배포 폴더에 Markdown을 복사하지 않는다.

ID는 소문자 영문·숫자·하이픈으로 구성하고 첫 글자는 영문 또는 숫자, 최대 80자다. ID와 `sourcePath`는 각각 유일해야 한다. 경로는 `docs/` 기준 상대 경로이며 `.md` 확장자를 사용한다. 절대 경로·상위 폴더 이동·백슬래시·외부를 가리키는 심볼릭 링크는 허용하지 않는다. 목록은 최대 1,000개이며 갱신일 내림차순, 동률이면 ID순으로 표시한다.

제목·설명·갱신일은 등록 목록이 기준이다. Markdown 첫 H1이 등록 제목과 같으면 화면의 제목으로 한 번만 표시한다. 문서 본문 안의 날짜나 버전은 원문을 유지한다.

## 수정과 등록 해제

- 수정은 원본 Markdown과 필요한 메타데이터를 함께 변경한다. 의미 있는 갱신 시 `updatedOn`을 직접 변경한다. 같은 문서를 갱신할 때는 ID를 유지해 기존 주소를 보존한다.
- 등록 해제는 목록에서 해당 항목을 제거한다. 원본 파일을 보관해도 웹에서 조회되지 않는다. 기존 상세 주소는 문서를 찾을 수 없다는 안내를 표시한다.
- 변경은 Git으로 검토·관리한다. 웹에서 업로드·수정·삭제하는 기능과 별도 업무 JSON 저장은 없다.

## 지원 문법과 링크

제목·순서/비순서 목록·강조·기울임·취소선·인용·표·구분선·인라인/블록 코드·링크·HTTP(S) 이미지와 Mermaid 흐름도/시퀀스 다이어그램을 지원한다. 수식·첨부파일 제공은 지원하지 않는다. 원시 HTML은 텍스트로 표시하며 스크립트·iframe·이벤트 속성은 실행하지 않는다. 렌더링은 markdown-it과 DOMPurify를 사용한다.

- 외부 HTTP(S) 링크는 새 창에서 `noopener noreferrer`로 연다.
- `[다른 문서](../guide.md)`처럼 현재 Markdown 파일을 기준으로 한 상대 링크는 등록된 문서일 때 앱의 상세 주소로 변환한다. 등록되지 않은 파일은 링크가 아닌 참고 텍스트로 표시한다.
- `## 1 결론`은 `#1-결론`으로 연결할 수 있다. 실제 제목 앵커에는 `doc-` 접두사를 붙이며 같은 제목이 반복되면 `-2`, `-3` 순번으로 구분한다. 목차는 렌더링된 제목의 정확한 앵커를 사용한다.
- `/Users/...`, `/private/...`, `file:`, 기타 허용되지 않는 주소는 레이블과 경로를 참고 텍스트로 표시한다. 서버 소스·로그·임의 파일은 제공하지 않는다.
- 이미지는 HTTP(S) 주소만 표시하며 최대 본문 폭으로 축소한다. 로컬 이미지·상대 이미지 파일은 참고 텍스트로 표시한다. 외부 이미지에는 지연 로딩과 `no-referrer`를 적용한다.

긴 표·코드 블록·다이어그램은 내부 스크롤을 사용한다. 제목·목록·문단·이미지는 화면 폭에 맞추고 본문은 Pretendard 15px/1.75를 사용한다. 목차와 문서 이동은 키보드로 조작할 수 있다.

### 워크플로우 다이어그램

`mermaid` 코드 블록의 `flowchart`/`graph` 흐름도와 `sequenceDiagram` 시퀀스를 그림으로 표시한다. `accTitle`은 다이어그램의 접근성 이름이며 `accDescr`로 흐름을 설명할 수 있다. 일반 문서에서는 엔진을 내려받지 않고, 다이어그램이 있는 문서를 열 때 앱 번들의 Mermaid12.2.0을 지연 로드한다. 외부 렌더링 서비스나 CDN으로 본문을 전송하지 않는다.

- 입력은 등록 문서의 Mermaid 코드 블록, 출력은 Pretendard를 사용하는 정제된 SVG와 접힌 원문이다. 한국어 글자를 축소하지 않도록 큰 그림은 내부 가로/세로 스크롤을 사용하고 키보드로 탐색할 수 있다.
- 문서별 설정 지시문, 클릭 동작, 사용자 스타일 지시문은 허용하지 않는다. 엔진의 strict 모드와 출력 SVG 정제를 함께 적용하며 링크·외부 이미지·이벤트 코드는 실행하지 않는다.
- 원문30,000자 초과, 지원하지 않는 구문, 문법 오류, 엔진 로드 실패 시 해당 그림만 안내와 펼친 원문으로 대체한다. 다른 그림과 본문은 계속 표시한다.
- 문서·계정·권한 변경 뒤 도착한 비동기 그림은 이전 본문에 적용하지 않는다. 문서 조회는 로그인 사용자에게 제공하며 업무 수정 권한과 분리한다.

등록된 [Foundry Photo 기술팀 자격 인증 워크플로우](FOUNDRY_PHOTO_WORKFLOW.md)에서 역할별 흐름3개·조직 필요자격 상속 예시1개·통합 시퀀스1개를 확인할 수 있다. 팀 자격 풀 준비와 팀·세부조직관리자의 조직별 필요자격 지정·상속 결과 확인을 구분한다.

## 조회 API와 권한

- `GET /api/system/documents` → `{ items: SystemDocumentSummary[] }`
- `GET /api/system/documents/:id` → `SystemDocumentDetail`

메타데이터는 `id`, `title`, `description`, `updatedOn`, `sourcePath`이고 상세에는 `markdown`이 추가된다. `sourcePath`는 문서 간 상대 링크를 해석하기 위한 문서 루트 기준 경로이며 서버의 절대 경로를 포함하지 않는다. 공유 타입은 `shared/src/documents.ts`에 정의한다.

기존 세션 인증을 두 API 모두에서 검사한다. API 경로와 응답 형식은 호환성을 위해 유지한다. 비로그인은401, 미등록 ID는404, 등록 목록 또는 파일 오류는 경로를 노출하지 않는503을 반환한다. 응답은 `no-store`로 제공한다. 문서/계정 변경 후 도착한 이전 응답은 버리고, 로그아웃·세션 만료 시 본문을 제거한다. 역할 변경만으로 문서 읽기 권한은 회수되지 않는다.

## 배포와 데이터 보존

현재 서버는 `server/src/`를 실행하므로 배포 루트에서 `server/`, `shared/`, `frontend/dist/`와 함께 **`docs/document-catalog.json` 및 등록한 모든 Markdown 파일**을 같은 상대 구조로 유지해야 한다. 프런트 파일만 배포하면 조회 API가 없고, 문서 파일을 누락하면 조회 오류가 발생한다.

문서는 서버 파일에서 조회하므로 재배포 시 함께 반영한다. 프런트 번들에는 문서 본문을 넣지 않는다. Vite의 파일 허용 범위도 확장하지 않는다. 문서 API 추가 시 실행 서버 재시작이 필요하며 기존 개발 실행의 업무·조직 파일 경로를 그대로 사용한다.

문서 등록은 업무/조직 JSON 스키마·revision·백업·초기화 대상에 영향을 주지 않는다. 업무 마스터 내보내기에는 이 문서를 포함하지 않으므로 서버 이전 시 코드와 문서 디렉터리를 별도로 함께 옮긴다.

### 다른 개발 환경에서 문서가 열리지 않을 때

저장소 루트에서 다음 순서로 확인한다. 문서 목록과 등록 원문4개는 Git에 포함되어 있으며 로컬 업무 데이터나 외부 문서 파일을 별도로 가져올 필요가 없다.

```sh
git pull --ff-only
npm ci
npm run documents:check:git
npm run dev
```

이미 서버가 실행 중이었다면 기존 개발 서버를 종료한 뒤 다시 실행하고 계정을 다시 선택한다. 프런트엔드만 새로 실행하고 API 서버가 이전 코드인 채 남으면 최신 문서 메뉴·조회 권한과 맞지 않을 수 있다. 기존 환경에서 `data:init`이나 테스트 데이터 초기화를 실행할 필요는 없다.

- 문서 검사가 실패하면 출력된 파일·목록 오류를 먼저 확인한다. 부분 체크아웃이나 소스 복사 시 `docs/`도 포함한다.
- 검사는 통과하지만 조회가 실패하면 브라우저 네트워크에서 `GET /api/system/documents`와 상세 요청을 확인한다. 401은 계정 재접속, 403은 이전 서버의 권한 검사 여부, 503은 실행 서버 쪽 문서 파일·목록 접근을 점검한다. 개발 프록시가 실제로 갱신한 API 서버를 가리키는지도 확인한다.
- API 서버는 자신의 `server/src/documents.ts` 위치를 기준으로 저장소의 `docs/`를 찾는다. 명령을 실행한 현재 폴더나 특정 개발자 PC의 절대 경로에 의존하지 않는다.
- 정적 실행은 `npm run build` 후 `npm start`를 사용한다. `frontend/dist/`만 복사하는 것으로는 문서 조회 API와 원문이 제공되지 않는다. 서버·공유 코드·등록 문서를 같은 배포 루트에 포함한다.
