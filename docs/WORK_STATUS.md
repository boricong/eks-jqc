# 업무 수행 상태와 장기 미수행 인증 말소

2026-10-29 도입. 업무 상태는 계정 접속/역할, 취득 대상자 Hold, 개별 인증의 Active/Hold/Revoke와 독립적이다. 업무 상태의 기본값은 Active다.

## 관리와 기간

- 인증 업무 관리 → 팀 사용자 관리에서 팀 관리자와 시스템 운영자가 개인별로 변경한다. 세부조직관리자는 변경할 수 없다. 팀 관리자는 시스템 운영자 계정을 변경하지 못한다.
- Active→Deactive는 현재 소속 Lv1의 유효 Auditee 인증1개 이상이 필요하다. Hold/만료/말소 인증은 제외한다. 다른 자격의 미완료 계획은 전환을 막지 않는다. Active 복귀에는 인증 보유 조건이 없다.
- 서버 KST 저장일에서 달력6개월을 더하고 다음날0시를 말소 기준으로 삼는다. 월말은 해당 월 말일로 조정한다. 2026-10-29 시작이면 2027-04-30부터 말소한다. 소급 설정은 제공하지 않는다. 동일 상태 저장은 구간을 갱신하지 않고, 복귀 후 다시 미수행하면 새 구간을 만든다.
- Deactive 동안 현재 팀 Auditee 계획/평가/발급/재인증 쓰기를 중단한다. 조회, 로그인, 관리자 업무, Auditor 절차는 유지한다. 유효기간과 일정은 연장하지 않는다.
- 조직 이동에도 시작일을 보존하고 최신 조직 ID 경로로 적용 팀을 판단한다. 현재 제품의 Lv1 간 사용자 이동 제한은 유지한다. 조직 재편 등으로 적용 팀이 바뀌면 이미 기한이 지난 구간도 새 팀을 검사한다.
- 화면 상태는 `active`/`deactive`로 표시한다. 변경창에는 이름과 상태 전환, 변경/취소만 제공하며 사유 입력과 설명은 표시하지 않는다. 전환 제한 사유는 목록 버튼의 툴팁으로 안내한다. 사유 생략 시 서버가 `관리자 업무 상태 변경`을 이력에 기록하며 기존 사유가 포함된 요청도 호환한다.
- 이 정책의 고정6개월은 자격 설정의 계획 최대 완료 개월과 별개다.

## 자동 처리와 복귀

서버 시작·1분 주기, 업무 조회/변경 전에 기한을 검사한다. 저장 큐 안에서도 확인하므로 말소 경계의 복귀/평가 제출은 기한 도래 처리를 우회하지 못한다. 변경이 필요한 경우 하나의 원자 저장에서 현재 팀 Auditee 인증을 Revoke로 변경하고 미완료 계획 요청·취득/재취득 배정·재인증 회차를 종료한다. Deactive는 유지한다. Hold 인증도 말소하지만 기존 Revoke는 재작성하지 않는다. Auditor와 다른 팀 인증은 유지한다.

계획 확정 내용, 답안, 수료, 최초 발급 및 버전 스냅샷은 보존한다. 처리 이력에는 미수행 구간, 처리 조직, 기준 시각과 실제 처리 시각을 기록한다. 서버 중단 중 지난 기한은 시작 시 보충하며 실패는 부분 반영 없이 재시도한다. 당사자와 관리자는 앱 내 결과 알림을 확인한다.

말소 전 복귀는 기존 효력·준비 조건에 따라 진행을 재개한다. 말소 후에는 현재 조직의 필요자격을 기준으로 관리자가 새 계획 요청을 보내고, 학습자는 전체 일정 수립 화면에서 확정한다. 이전 인증은 복원하지 않고 새 배정·수강·평가 근거를 만든다. 기존 Hold나 조직 사용 중지, 역할/준비 부족은 복귀로 해제되지 않는다.

Auditee 현황의 지표·실적·차트에서 Deactive를 제외한다. 전체/제외 인원 목록으로 기록을 조회할 수 있지만 KPI에는 포함하지 않는다. Hold/비활성 조직과 겹치는 제외 인원은 사람 ID 기준으로 한 번만 집계한다. Auditor 현황은 유지한다.

## 공개 계약

- 업무 스키마30, 쓰기 헤더 `X-EKS-Release-Contract: 3`. 계획 workflow v7과 확정 근거 형식은 유지한다.
- 사용자 `workStatus`, `workDeactivation`은 현재 상태와 구간을 보관한다. 복귀 시 현재 구간은 제거하고 lifecycleEvents의 `work_status` 이력에 이전 구간을 남긴다. 사용자 일반 편집은 업무 상태를 변경하지 않는다.
- 팀 사용자 조회의 `workStatusInfo`는 상태/기간, 현재 팀 유효 인증 수, 변경 가능 여부와 보류 사유를 제공한다.
- `POST /api/team-users/:id/work-status/preview`: 입력은 status/revision/organizationRevision과 선택 reason, 출력은15분 확인 토큰·기준일·중단 대상 건수다. 권한/소속/유효 인증을 검사한다.
- `PUT /api/team-users/:id/work-status`: token과 Idempotency-Key를 사용한다. 실행 직전 사용자·팀·조직·업무 revision·데이터 세대·KST 날짜·토큰 기한을 재검사한다. 권한 부족403, 기준 변경409, 진입 조건 미충족422. 같은 요청 키는 최초 결과를 반환한다. 서버 재시작 후 새 실행은 미리보기를 다시 받되 완료된 요청의 영수증은 유지한다.
- 기존 종료 API `/api/testing/*`, `/api/system/master-data/*`는 그대로410이다. 새 파일 업로드/다운로드 기능은 없다.

## 이관과 복구

`npm run data:migrate-work-status`는 기본 dry-run이다. 서버 중지와 업무·조직·관리 정보 및 소스 백업 후 출력된 revision/SHA256을 확인하여 `--apply --expected-revision=... --expected-sha256=... --organization-sha256=...`로 실행한다. 기존 사용자를 Active로 지정하고 업무 스키마/전체 revision 및 저장소 세대를 갱신한다. 인증·진행·발급 근거를 변경하거나 과거 기간을 추정하지 않는다. 재실행은 무변경이다. 실패하면 이전 호환 소스와 세 데이터 파일을 함께 복원한다.

기존 내장 테스트 초기화는 사용자 목록을 보존하므로 업무 상태와 현재 구간도 유지한다. 인증이 사라진 Deactive 인원도 관리자가 Active로 복귀시킬 수 있다. 일반 신규 사용자는 Active로 생성한다.
