# 요청 전체 자격 일정과 완료 기한 운영

2026-10-29 · 업무29 · 조직4 · personal-certification-v7 · 쓰기 계약2

## 대상과 화면

Auditee 취득·재취득의 관리자 요청에 포함된 필요자격 전체를 /plans?request=:id에서 작성한다. 최신 요청을 기본 표시하며 이전 요청도 선택할 수 있다. 이전 learner_choice 요청의 허용된 추가 자격은 같은 화면에서 선택한다. Auditor와 별도 재인증은 기존 절차를 유지한다.

상단 관리자 안내문·작성 기한·대상 수 아래에 일괄 시작일/완료일/전체 적용을 표시한다. 자격마다 날짜 두 개를 제공하고 선택 목표(2,000자)와 포함 인증Set은 펼쳐 본다. 인증Set별 일정은 없다. 취득/진행 중은 읽기 전용이며 준비 부족 대상도 사유와 함께 남는다. 일괄 적용은 편집 가능한 전체에 적용하고 덮어쓰기는 확인받는다. 하나라도 날짜 역전·기한 초과이면 아무 값도 바꾸지 않고 문제 자격과 가장 빠른 허용 완료일을 안내한다.

기본 일정은 서버 KST 오늘+7일 시작, 시작+21일 완료다. GET은 초안을 생성하거나 날짜를 다시 쓰지 않는다. 수정/삭제한 날짜는 자동 보정하지 않는다. 초안은 자동 저장하며 빈 날짜·역전 날짜도 보관할 수 있다. 전체 계획 확인 → 검토 → 전체 계획 확정으로 요청 완료까지 함께 저장한다. 취득/진행 중인 자격만 있으면 추가 계획 대상 없음 확인을 사용한다. 이전 초안 주소는 해당 요청/자격으로 연결하며 확정·종료된 기록은 읽기 전용 상세를 유지한다.

## 완료 기한

팀 자격 설정의 planningDeadlineMonths는 Auditee 취득 자격에 필수이며 1~1,200의 정수다. 신규 등록은6개월, 변경은 자격 마이너 버전이다. 기존 편집 권한을 유지하며 세부조직관리자 권한을 추가하지 않는다. 상세 조회·저장 미리보기·기준 변경 재확인에 개월을 표시한다.

최종 확정일(KST)에 달력 기준 N개월을 더한다. 해당 일이 없으면 말일을 사용하고 기한 당일까지 허용한다. 작성 중에는 서버 오늘 기준 예상 기한을 표시한다. 확정은 planningWindow의 baseOn/months/deadlineOn과 qualificationPolicySnapshot의 개월을 고정한다. 이후 설정 변경은 기존 계획에 영향을 주지 않는다. 기한은 일정의 허용 상한이며 학습·평가·수료·인증 중단 기준이 아니다.

## API·리뷰·원자성

인증·본인 요청·현재 소속·Hold·요청 상태 검사를 유지하며 쓰기는 X-EKS-Release-Contract: 2와 기존 세대·Idempotency-Key가 필요하다.

| API | 입력 | 출력/동작 |
| --- | --- | --- |
| GET /api/planning-requests/:id/schedule | 요청ID | 전체 행·기존 계획·버전·준비 상태·기한·허용 행동. 쓰기 없음 |
| PUT /api/planning-requests/:id/schedule | requestRevision, rows(entityId, qualificationId, planId/revision, startOn/endOn/goal, 선택 reviewedCriteriaToken) | 변경 계획의ID/revision. 초안 재사용, 없을 때만 생성 |
| POST /api/planning-requests/:id/schedule/preview | 빈 본문 | 전체 행·항목별 errors·canComplete·서버일·reviewToken |
| POST /api/planning-requests/:id/schedule/complete | requestRevision, reviewToken, 선택 confirmNoAdditional | 전체 계획/배정/수강/기준 고정/요청 완료 단일 트랜잭션 |

검토 토큰은 요청·조직revision·사용자 권한/소속·계획revision/내용·최신 기준·기한·KST 날짜·기존 완료 근거를 묶는다. 검토 후 바뀌면409이며 일정/목표를 유지해 재검토한다. 날짜 오류는 행/입력란별로 안내하며 전체 확정을 보류한다. 기준 변경은 이전/최신 버전과 개월을 보여주고 명시 동의한 토큰으로만 교체한다.

저장 실패/응답 유실은 동일 요청 키로 재시도한다. 일부 행만 저장·확정하지 않는다. 충돌은 서버 날짜와 내 입력을 비교한 뒤 내 입력을 유지하고 재검토한다. 이동 전 저장 실패는 폐기 확인을 받는다. 계정·요청·데이터 세대가 바뀐 뒤 도착한 응답은 이전 화면에 적용하지 않는다. 구형 쓰기는410으로 새로고침을 요구한다. 단건 계획 확정도 동일한 기한을 검사하며 제품은 개별 확정 버튼을 제공하지 않는다.

## 업무28 →29 명시 이관

npm run data:migrate-planning-schedule -- --dry-run으로 대상을 재산정한다. 적용은 서버 종료·3파일 및 소스 백업 후 --apply --expected-revision=N --expected-sha256=... --organization-sha256=...를 사용한다. 저장소는 잠금 아래 원본 해시를 다시 검사하고 관리 정보의 세대를 함께 교체한다. 일반 시작은 자동 이관하지 않는다.

최신 비삭제 Auditee 취득 자격 중 필드가 없는 버전만6개월의 새 마이너로 추가한다. Ready는 같은ID·버전 미확정·상태를 유지하고6개월만 설정한다. Auditor·재인증·과거 자격은 변경하지 않는다. 기존 초안의 일정/참조버전과 확정 계획·배정·평가·발급/고정해시는 그대로 둔다. 과거 필드 부재는 읽기 호환이며 기본값으로 재작성하지 않는다. 재실행은 무변경이다. 새 개발/내장 데이터의 팀 자격 등록에도6개월 기본값을 사용한다.

검증 → 서버 중지 → 업무/조직/maintenance·소스 백업 → dry-run → revision/해시 조건부 이관 → 허용 변경 외 근거 대조 → 재시작 → 실제 저장 없는 조회 확인 순서다. 실패 시 이전 코드와3파일을 함께 복원한다. 현재 데이터를 초기화하거나 다시 로드하지 않는다.

### 자격 단위 보존 이관

시작일은 원래 학습 시작일 중 최소, 종료일은 원래 목표 인증일이며 목표가 없는 초안은 원래 학습 완료/평가일 중 최대다. 값이 없으면 빈 상태를 유지한다. 목표 하나는 그대로 옮기고 여러 목표는 인증Set 이름과 합친다. 합친 길이가 2,000자를 넘으면 새 목표는 비우고 원문을 참고해 정리하도록 표시한다.

previousSchedule에 이전 workflow·목표 인증일·인증Set 일정·목표·이관 시각·목표 재검토 여부를 보존한다. 개인/기존 계획 조회 권한의 관리자만 이전 이력을 읽으며 운영 일정과 집계에 사용하지 않는다. 계획 ID·상태·배정/요청 연결·기존 완료 근거를 유지하고 revision+1·updatedAt·workflow v6와 기본값 적용 표식만 함께 갱신한다. 전체 revision+1과 감사에 변환 전후를 기록한다. 재실행은 무변경이며 잘못된 날짜/인증Set 참조가 있는 기존 확정 계획은 이관을 보류한다.
