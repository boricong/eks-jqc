# 내장 테스트 데이터 관리

2026-10-27 확정 계약. 시스템 운영 → **테스트 데이터 관리**(`/system/test-data`)는 시스템 운영자에게 **테스트 데이터 로드 / 전체 데이터 초기화**만 제공한다. 제품 배포 자체로 데이터를 바꾸지 않는다. 파일 선택·이전·선택 삭제·진행만 초기화·이전 환경 복원은 제공하지 않는다.

## 초기화와 보존 범위

전체 초기화는 테스트 여부에 관계없이 기본자격·팀 자격·공통/팀 인증Set·모든 버전·공통 반영 보류·필요자격 지정·상속 예외·Auditor 안내·계획·배정·학습·평가·주관식·수료·인증·재인증·공지·알림·업무/조직 이력·업무 재시도 기록을 삭제한다. 과거 관리 정보에 남은 테스트 업무 스냅샷도 제거한다. **기존 인증서와 버전 이력도 모두 삭제된다.**

사용자 객체의 모든 필드(계정·역할·소속·관리 권한·Auditor 지정·취득 가능 상태·revision)는 그대로 보존한다. 조직은 ID·이름·상하위 구조·사용 상태를 유지하고 설명·담당 업무와 이력/요청을 비운다. 저장소 revision은 증가한다. 자동 백업·저장소 세대·최소 실행 영수증은 업무 건수에서 제외하며 복구·중복 방지를 위해 보존한다.

## 로드할 구성

- `server/src/test-data-templates.ts`의 고정 원본19개를 사용한다. 구현 당시 기본자격의 ID·이름·영문명·설명·유형·소유 범위·Auditor 등급/선행 기준을 그대로 고정했다. 시험 중 변경한 운영 데이터로 원본을 갱신하지 않는다.
- 공통 원본5개(Auditee3 / Auditor2), 활성 Lv1마다 특화10개(Auditee6 / Auditor4)를 생성한다. 팀 자격·팀 공통 사본·인증Set 연결·조직 필요자격은 생성하지 않는다. 기본자격의 공통 기본 목록도 변경하지 않는다. 생성한 인증Set은 최초 `v1.0`이다.
- 내장 구성 버전3: Auditee는 인증Set별 지식3·상황3·주관식1개다. 지식·상황 각각 선택지4개·문항 순서대로34/33/33점(총100점)·합격100점이며 **정답은 모두 첫 번째 선택지**다. 질문 끝에 실제 정답 번호 `(정답: 1번)`을 표시한다. 주관식 답변은 채점·수료 조건에 포함하지 않는다. 새 실행 영수증은 구성 버전3으로 기록하고 기존 버전1·2 영수증과 동일 요청 재시도의 결과는 보존한다. 자격·인증Set의 최초 내용 버전 `v1.0`과 구분한다.
- Auditor는 평가 문항 없이 필수 교육 본인 확인을 사용한다. 교육3종(MTC/팀 특화/OJT), 자료4종(직접 작성/EDM/Confluence/일반 URL)을 제공한다. 링크는 편집용 예시 주소다.
- 팀 관리자가 자격 풀 선택 → 팀 등록 → 인증Set·기간 등 운영 기준 설정 → Active 전환부터 직접 시험한다. Auditee는 이후 조직 필요자격 지정 → 계획 요청 → 학습자 계획·최종 확인 → 학습·평가 → 수료·인증서 순서로 진행한다. Auditor는 등록·기준 설정 후 기존 자율 학습을 사용한다. 업무28·조직4를 유지하며 데이터 이관은 없다.
- 역할이나 등급을 이름으로 추정하지 않는다. 기존 계정 역할은 변경하지 않으며 필요한 Auditor 지정은 일반 사용자 관리에서 수행한다. 등급이 없는 Auditor 기본자격은 시스템 운영자가 보완해야 팀 등록할 수 있다. 팀별 Auditor 지정 안내문은 기존처럼 생성한다. 없는 메인 Auditor 기본자격을 추가하지 않는다.

## 공개 API와 확인·보류 계약

| API                                          | 입력 / 출력                                                                                     |
| -------------------------------------------- | ----------------------------------------------------------------------------------------------- |
| `GET /api/system/test-data`                  | 현재 건수·보존 수·내장 구성·활성 팀·준비 부족·로드/초기화 가능 여부·현재 자격 목록              |
| `GET /api/system/test-data?operationKey=...` | 같은 실행자 계정의 최소 영수증 추가 조회. 미완료이면 `operation: null`이며 자동 재실행하지 않음 |
| `POST /api/system/test-data/preview`         | `{ action: "load" \| "reset" }` → 확인 ID·15분 만료·전후 건수·보존 수·안내                      |
| `POST /api/system/test-data/apply`           | `{ action, previewId, confirmation }` + `Idempotency-Key` → 영수증·세 파일 백업 경로·새 세대    |

로드 구성의 `qualifications`, `commonCopies`는 항상0이며 미리보기의 팀 자격·조직 필요자격 생성 건수도0이다. 현재 팀 자격 목록은 사용자가 수동 등록한 실제 자격만 조회한다. 기존 로드 데이터에는 소급 적용하지 않는다. 새 구성을 사용하려면 사용자가 전체 초기화 후 다시 로드한다. 배포 시 실제 초기화·로드를 실행하지 않는다.

초기화 확인 문구는 `전체 초기화`, 로드는 `테스트 로드`다. 로드는 업무·조직 부가 정보·과거 업무 스냅샷이 전부 비어 있을 때만 허용한다. 비어 있으면 초기화 버튼은 비활성이다. 활성 팀이 없거나 원본의 소유 팀이 없어도 로드를 보류한다.

실행 시 시스템 운영자 권한·업무/조직 revision과 전체 내용 해시·세대를 다시 검사한다. 확인 후 변경·15분 만료는409, 문구 오류는422다. 미리보기·취소는 저장하지 않는다. 동일 키/동일 요청은 재시작 후에도 최초 영수증만 반환하고, 동일 키의 다른 요청은409다. 확인 정보는 메모리에 두므로 실행 전 서버 재시작은 다시 확인해야 한다.

업무·조직·관리 정보의 원본 바이트를 각각 자동 백업하고 중단 표식을 쓴 뒤 교체한다. 파일 중 하나라도 저장에 실패하면 세 파일 원본 바이트로 롤백한다. 롤백 실패·프로세스 중단 시 일반 기동을 막고 서버를 중지한 상태에서 `npm run data:recover-master`로 동일 작업의 세 파일을 복구한다. 백업과 표식을 먼저 보존한다. 일반 파일 복원보다 교체 복구 절차를 우선한다.

성공하면 모든 세션과 교체 전에 대기한 쓰기를 차단한다. 브라우저는 새 세대를 관찰하면 계정·업무 상태와 이전 세대 초안을 무효화한다. 실행자 브라우저의 최소 요청 키로 재접속 후 해당 메뉴에서 영수증을 조회한다. 응답 유실 시에도 자동 재실행하지 않는다. 실제 데이터에 배포 검증용 로드·초기화를 실행하지 않는다.

## 폐지 기능과의 관계

이 새 메뉴는 종료된 테스트 관리·데이터 관리와 별개다. 과거 `/system/testing`·`/system/data`는 계속 조직 관리로 이동하고 `/api/testing/*`·`/api/system/master-data/*`는 인증·시스템 운영자 확인 후410 `FEATURE_REMOVED`다. 과거 요청이나 본문은 실행하지 않는다. 파일 이전·조직별 진행 초기화·테스트 소유 데이터만 삭제·Photo 생성 CLI는 계속 종료 상태다. 기존 관리 영수증의 읽기 호환과 CLI 백업/복구는 유지한다.

## 검증

임시 저장소와 실제 업무 API로 고정19개·정확한 분포·계정/조직 보존·전체 배열 삭제·과거 스냅샷 제거·반복 로드·중복 차단·확인 만료/충돌·세 파일 실패 롤백·중단 복구·동시 쓰기·재시도/재시작·과거 세대 차단을 검사한다. 로드 후 팀 자격/공통 사본/조직 필요자격/진행0과 기본자격19·공통5·팀별 특화10을 확인한다. 수동 기본 목록 지정 후 등록 또는 기본 목록 없이 등록 후 자격 설정에서 공통 원본 선택·사본 생성·팀 운영 기준 저장·조직 지정 후 Auditee 전체 인증, Auditor 등급 보완·수동 등록·Active·기존 계정 지정/본인 확인, 원본 버전 전파와 초기화도 검증한다. 브라우저는 네 폭1920/1440/768/390px·키보드·취소·오류 입력 보존·응답 유실 조회와 인증 절차를 시험한다.

## 내장 테스트 데이터 관리 당시 계약

시스템 운영 → 테스트 관리는 외부 파일 선택 없이 서버 코드에 내장된 구성을 현재 데이터에 **추가**한다. 사용자 계정·역할·소속, 조직, 기본자격, 등록된 자격·인증Set과 기존 진행 기록은 유지한다. 기존 환경 전체를 교체하거나 과거 상태로 복원하는 기능이 아니다.

## 구성과 사용

- 공통 원본 5개: Auditee 3개, Auditor 2개.
- 활성 Lv1 팀마다 특화 인증Set 10개: Auditee 6개, Auditor 4개.
- 각 팀의 미등록 기본자격만 새 자격으로 만든다. 같은 팀·기본자격의 과거/삭제된 등록도 건너뛰어 계보를 중복 생성하지 않는다. 팀 소유 기본자격은 소유 팀에만 등록한다.
- 새 자격에는 같은 유형의 공통 사본 1개와 특화 1개를 연결한다. 모든 새 버전은 v1.0이다. 기존 자격에는 테스트 인증Set을 자동 연결하지 않는다.
- Auditee 인증Set마다 지식3·상황3·주관식1을 제공한다. 객관식은 선택지4개·각1점·정답 첫 선택지·합격70점이다. 주관식은 수료와 독립된 답변 수집이다.
- Auditor는 기존 정책에 따라 평가 문항 없이 교육·자료와 필수 교육 본인 확인을 사용한다. 기본자격 등급·선행 조건을 추정하거나 수정하지 않는다. 준비되지 않은 등급 또는 같은 팀의 기존 Active 등급과 충돌하는 새 자격은 Hold로 생성한다.
- 모든 인증Set에 교육3종과 자료4종을 넣는다. 직접 작성 자료는 내부 본문이며 나머지 example.com 링크는 유형 편집용 예시다. 실제 사내 EDM/Confluence 접근을 대신하지 않는다.
- 기간제12개월과 무기한 정책을 섞고, 기간제의 재인증 시작3개월·알림7일을 설정한다. 기존 팀 Auditor 안내문은 유지하며 안내문 자체가 없는 팀에만 시험용 안내문을 추가한다.

운영자가 로드 내용을 확인하고 실행한 뒤 계정을 다시 선택한다. 새 테스트 자격을 팀 조직의 필요자격에 지정하고 계획 요청 → 자격 선택 → 일정·최종 확인 → 학습·평가 → 수료·인증서로 진행한다. Auditor는 기존 계정의 지정과 등급·선행 일반 인증을 충족한 뒤 시작한다. 빠진 기본자격 설정과 팀 관리자 계정은 화면에서 안내하며 계정이나 기본자격을 자동 보완하지 않는다.

## 초기화와 삭제 범위

| 동작                    | 기준                                                      | 진행                                                                          | 기존 데이터                            |
| ----------------------- | --------------------------------------------------------- | ----------------------------------------------------------------------------- | -------------------------------------- |
| 로드                    | 공통5·팀별 특화10·미등록 자격 추가                        | 자동 진행/배정 없음                                                           | 유지                                   |
| 테스트 진행 초기화      | 편집한 테스트 기준·버전 유지                              | 테스트 기준에 연결된 계획·배정·응시·답변·수료·인증·갱신과 관련 알림/이력 정리 | 별도 진행 유지                         |
| 처음 상태로 다시 로드   | 기존 테스트 세트 제거 후 현재 기본자격의 빈 자리에 재생성 | 해당 테스트 진행 정리                                                         | 별도 기준·진행 유지                    |
| 테스트 데이터 전체 삭제 | 테스트 원본·사본·특화·자격과 파생 버전 제거               | 해당 테스트 진행 정리                                                         | 기존 및 무관하게 추가한 업무·계정 유지 |

내부 관리 정보는 생성한 공통 원본 ID, 팀 인증Set 계보, 자격 계보와 로드 전 참조 정보를 저장한다. 삭제 범위는 표시명이나 사용자 계정이 아닌 ID와 연결 관계로 계산한다. 테스트 원본에서 나중에 가져온 팀 사본, 자동 전파 버전, 테스트 인증Set을 연결해 생긴 자격 버전과 그 후속 버전도 포함한다. 학습자 ID만 같다는 이유로 다른 인증 절차를 삭제하지 않는다.

여러 자격을 담은 계획 요청은 테스트 선택·완료 근거만 제거하고 다른 선택/계획을 보존한다. 테스트만 담은 신규 요청은 삭제한다. 조직 필요자격에서 테스트 계보만 제외하며 다른 지정은 유지한다. 기존 사용자·조직·기본자격의 일반 수정과 무관한 공지 등은 삭제 대상이 아니다. 자동 백업과 최소 실행 영수증은 복구를 위해 유지한다.

- 기존 진행 기록이 테스트 기준과 충돌하면 기존 기록을 삭제하지 않고 `TEST_EXTERNAL_REFERENCE`로 보류한다. 전용 테스트 자격으로 진행한다.
- 기본자격의 기본 공통 목록에 테스트 원본을 수동 연결했다면 목록에서 먼저 제외해야 삭제/재로드할 수 있다. 기본자격은 자동 수정하지 않는다.
- 전체 설정 초기화/JSON 이전은 로드된 테스트 데이터의 소유 정보를 잃지 않도록 테스트 삭제 후에만 실행한다. 기존 기능은 시스템 운영 → **데이터 관리**로 이동했다.

## 공개 계약과 저장

| API                                           | 입력/출력                                                                                 |
| --------------------------------------------- | ----------------------------------------------------------------------------------------- |
| `GET /api/testing/environment`                | 운영자 전용 로드 상태·구성·기존 등록 건너뜀·보완 안내·테스트 진행 건수                    |
| `POST /api/testing/environment/preview`       | `{ action: load/reset/reload/delete }` → 확인 ID·만료·전후 기준 수·보존 수·삭제할 진행 수 |
| `POST /api/testing/environment/apply`         | `{ action, previewId, confirmation }`와 `Idempotency-Key` → 영구 실행 영수증              |
| `GET /api/system/master-data/operations/:key` | 재접속 후 영수증 조회. 미실행 요청을 자동 실행하지 않음                                   |

확인 문구는 각각 `테스트 로드`, `진행 초기화`, `다시 로드`, `테스트 삭제`다. 판정과 대상 계산은 서버가 담당한다. 같은 운영자·동작·요청 키의 재시도는 최초 결과만 반환한다. 다른 내용이나 운영자로 같은 키를 재사용하면409다. 작업 전후 업무·조직 revision을 각각 증가시키며 모든 세션·이전 세대 쓰기를 차단한다. 워크스페이스의 `testEnvironment` 플래그는 공통 안내 표시용이며 원본·정답·보존 정보를 노출하지 않는다.

레시피는 `server/src/test-environment.ts`에 내장한다. 사용자가 업로드할 별도 데이터 파일은 없다. 소유 정보와 보존 참조는 기존 `.maintenance.json` 내부의 선택적 `testEnvironment`에 저장한다. 업무26·조직4·JSON15는 유지하며 관리 정보 스키마1에 선택 필드를 추가했다. 서버 재시작 후에도 소유 정보·해시·원본 참조 충돌을 검사한다. 활성 테스트의 관리 정보는 설정 JSON 내보내기로 옮기지 않는다.

세 파일의 기존 교체 트랜잭션·영구 사전 백업·중단 표식을 사용한다. 하나라도 실패하면 업무·조직·관리 정보 모두 되돌리고, 복구 실패 시 서버를 차단한다. 복구는 [설정·기준 복구 절차](MASTER_DATA.md)의 같은 접미사 백업 쌍과 관리 정보를 함께 사용한다. 활성 테스트가 있으면 삭제 후 이전 코드로 전환한다. 관리 정보만 삭제하면 테스트의 소유 관계를 잃으므로 수동 삭제하지 않는다.
