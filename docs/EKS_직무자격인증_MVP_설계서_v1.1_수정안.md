# EKS 직무자격인증 MVP 설계 수정안

버전 1.1 · 2026년 10월 15일 · 검증용 MVP

구현 결정 반영: 2026년 10월 16일 — JSON 저장, 세션, 과정별 실제 수행 비교 추가

EKS는 자격, 과정, 평가 항목을 등록하고 평가 결과를 과정 수료와 자격 인증으로 연결하는 범용 시스템이다. 이번 MVP는 객관식과 FT 실기를 함께 평가하고, 일부 평가의 재응시부터 검증용 인증까지 처리한다. 평가 내용과 합격 기준은 등록 데이터로 관리한다.

검증의 우선 목적은 평가 기준이 실제 직무수행의 최소 요건을 판단하는 데 적절한지 확인하는 것이다. 시스템 동작은 샘플 데이터로 검증하고, 평가 기준의 적절성은 실제 평가 내용과 별도로 확보한 수행 근거를 비교하여 확인한다. 생성한 인증은 검증용 기록이며 실제 사내 자격으로 인정하지 않는다.

## 1 확정한 업무 규칙

| 항목 | 확정 내용 |
| --- | --- |
| 검증 목적 | 평가 기준이 실제 직무수행의 최소 요건을 판단할 수 있는지 확인 |
| 인증의 용도 | 검증용 기록으로만 사용 |
| 평가 방식 | 객관식과 FT 실기 모두 지원 |
| 과정의 평가 구성 | 한 과정에 객관식과 실기를 함께 둘 수 있음 |
| 혼합 과정의 수료 | 객관식과 실기 각각의 기준을 모두 충족해야 수료 |
| 재응시 | 동일한 기준에서는 통과한 평가를 유지하고 미통과한 평가만 재응시 |
| 인증 확정 | 자격의 모든 필수 과정 수료 시 검증용 인증 자동 생성 |
| 샘플의 의미 | Recipe Management와 과정명은 기준정보의 예시이며 시스템 업무 기능을 뜻하지 않음 |
| 샘플 정답 | ‘재검토’는 해당 객관식 문항의 정답이며 별도의 검토 절차나 승인 기능을 뜻하지 않음 |

실기 수행 조건으로 확인한 ‘매뉴얼 참고 가능, 다른 사람의 도움 없이 수행’은 평가 안내와 판정 기준의 데이터로 표현한다. 구체적인 실기 항목은 별도로 등록하며, 시스템이 도움 여부를 자동으로 탐지하는 기능은 포함하지 않는다.

이하의 기능 축소, 화면 구성, 구현 구조는 위 결정을 반영한 MVP 설계안이다. 범위 축소안을 사내 운영정책으로 사용하지 않는다.

## 2 코어 프로세스와 개념

**기준 등록 → 대상자에게 자격 배정 → 객관식 및 FT 평가 → 과정 수료 → 필수 과정 충족 확인 → 검증용 인증 자동 생성 → 결과와 근거 조회**

| 개념 | 의미 |
| --- | --- |
| Qualification 자격 | 취득에 필요한 필수 과정의 집합 |
| Course 과정 | 수료를 판정하는 단위. 하나 이상의 필수 평가로 구성 |
| Item 평가 항목 | 객관식 문항 또는 실기 판정 항목 |
| Attempt 응시 | 특정 과정의 객관식 또는 실기 평가를 수행한 한 번의 기록 |
| Completion 수료 | 해당 과정의 필수 평가를 모두 충족한 사실 |
| Certification 인증 | 자격의 모든 필수 과정 수료에 따라 자동 생성한 검증용 기록 |

기준 구조는 Qualification → Course → Item을 유지한다. 과정 안에서 객관식과 실기의 문항, 기준, 응시 결과를 각각 묶어 관리한다. 필기와 Case는 같은 객관식 기능을 사용하고, 필요한 구분은 분류 데이터로 둔다.

과정별 필수 평가 구성은 객관식만, 실기만, 객관식과 실기 중 하나로 지정할 수 있도록 한다. 지정된 필수 평가를 모두 충족해야 수료하며, 평가가 없는 과정은 배정할 수 없다.

학습자료 URL은 과정에 등록할 수 있다. 링크 열람은 수료 근거로 사용하지 않는다. 별도의 교육 참여 확인이나 학습시간 추적은 이번 범위에 포함하지 않는다.

## 3 평가와 수료 판정

### 평가별 판정

객관식은 문항, 선택지, 정답과 배점을 등록하고 서버에서 채점한다. 객관식을 필수로 지정한 과정에는 적어도 하나의 문항이 있어야 하며, 문항마다 두 개 이상의 선택지와 단일 정답, 양수 배점을 요구한다. 합격 기준은 과정의 객관식 평가 설정값으로 저장한다. 원문에 제시된 90점과 100점은 확정된 합격 기준으로 사용하지 않는다.

실기는 지정된 FT가 모든 항목의 Pass 또는 Fail과 판정 근거를 기록한다. 모든 필수 실기 항목이 통과하면 합격한다. 실기를 필수로 지정한 과정에는 적어도 하나의 필수 실기 항목이 있어야 한다. FT는 자신을 평가할 수 없다. 최종 평가자와 확정 시각을 응시에 저장한다.

객관식과 실기의 점수를 합산하여 서로의 미통과를 상쇄하지 않는다. 객관식 정답, 점수, 문항별 결과와 실기 판정 근거는 검증 담당자가 확인하고, 학습자에게는 평가별 진행 상태와 통과 여부를 제공한다.

### 혼합 과정의 수료 상태

| 객관식 | 실기 | 과정 상태와 다음 행동 |
| --- | --- | --- |
| 미응시 | 미평가 | 미시작 |
| 통과 | 미평가 | 진행 중, 실기 평가 필요 |
| 미통과 | 통과 | 미수료, 객관식 재응시 |
| 통과 | 미통과 | 미수료, 실기 재평가 |
| 미통과 | 미통과 | 미수료, 각 평가 재응시 |
| 통과 | 통과 | 과정 수료 생성 |

실기만 지정한 과정은 실기 통과로, 객관식만 지정한 과정은 객관식 통과로 수료한다. 지정하지 않은 평가를 대기 상태로 표시하지 않는다.

과정 수료는 개별 평가 제출 처리에서 공통 판정 함수를 호출하여 확인한다. 한 평가만 통과한 경우에는 평가 결과만 저장한다. 마지막 필수 평가가 통과하면 수료 기록과 각 평가의 합격 근거를 함께 저장한다.

### 재응시

통과한 평가는 같은 수강과 같은 기준 버전 안에서 유지한다. 미통과한 평가만 새 응시를 생성하며, 실패한 응시도 이력으로 보존한다. 예를 들어 객관식 통과 후 실기에서 실패하면 다음 실기 평가가 통과했을 때 기존 객관식 합격 기록과 새 실기 합격 기록으로 수료한다.

이미 통과한 평가의 추가 응시는 만들지 않는다. 진행 중인 응시가 있으면 이를 이어서 수행하며, 같은 수강의 같은 평가 종류에 진행 중인 응시는 하나만 허용한다. 객관식과 실기의 진행 상태는 각각 관리한다.

검증용 MVP의 축소안은 재응시 횟수와 대기시간 제한을 두지 않고 이력을 기록하는 것이다. 실제 제도 운영에 필요한 횟수 제한, 유예기간, 예외 승인 기능은 후속으로 분리한다.

### 기준 변경

배정할 때 자격, 과정, 문항, 정답, 판정 기준의 버전을 고정한다. 진행 중인 과제의 기준을 바꾸지 않는다. 개정 기준을 검증하려면 새 버전으로 새 검증 과제를 배정한다.

다른 기준 버전, 다른 수강, 다른 자격 과제로 합격 결과를 자동 이관하는 기능은 이번 범위에서 제외한다. 과정 정의를 여러 자격에 연결하는 구조는 유지하되, 과거 수료 결과의 자격 간 자동 재사용은 별도로 다룬다.

자격·과정의 고정 식별자 `entityId`와 버전 식별자 `id`를 구분한다. 사용 등록한 기준은 수정하지 않으며, 서버가 계보 안의 다음 버전 번호를 부여한다. 초안 수정에는 `revision`을 사용해 다른 창의 변경을 덮어쓰지 않는다.

FT를 변경할 때 사유·변경자·시각을 기록하고 진행 중 실기의 기존 판정·근거를 감사 이력에 보존한다. 같은 요청과 응시 회차를 유지하면서 새 FT에게는 빈 초안을 제공한다. 이미 확정한 평가자와 결과는 바뀌지 않는다. 이전 FT의 늦은 저장·제출은 거부한다.

## 4 검증용 인증

인증 조건은 검증에서 제외되지 않은 과제에 지정된 비어 있지 않은 필수 과정 집합 전체에 유효한 수료 기록이 존재하는 것이다. 모든 수료는 같은 과제의 수강에서 생성되어야 하며, 대상 직원과 배정된 과정 버전이 일치해야 한다.

마지막 필수 과정이 수료되면 검증용 인증을 자동 생성한다. 인증 담당자의 별도 승인, 반려, 재검토 대기 상태는 두지 않는다. 화면과 결과 자료에는 검증용 인증임을 표시한다.

인증 근거에는 각 필수 과정의 수료 기록을 연결한다. 수료 기록에서는 객관식과 실기의 합격 응시까지 추적할 수 있어야 한다. 수료증이나 인증서 PDF를 생성하지 않아도 수료와 인증 사실을 확인할 수 있다.

평가 제출, FT 판정 또는 인증 처리 요청이 반복되거나 동시에 도착해도 같은 수강의 수료와 같은 과제의 인증은 각각 한 번만 생성한다.

## 5 MVP 필수 기능과 후속 범위

### 필수 기능

| 기능 | 최소 구현 |
| --- | --- |
| 사용자와 접근 범위 | 검증 참여자 사전 등록, 학습자·FT·운영자 구분, 서버에서 본인·배정 관계 확인 |
| 기준 등록 | 자격·필수 과정·객관식 문항·실기 항목·합격 기준 등록과 기본 수정 |
| 기준 고정 | 입력 검증 후 배정 가능한 버전으로 고정하고 과거 버전 보존 |
| 자격 배정 | 운영자가 대상자에게 자격을 직접 배정하고 실기 FT 지정 |
| 객관식 평가 | 응시, 답안 제출, 서버 채점, 평가별 재응시 이력 |
| 실기 평가 | 지정 FT의 항목별 판정과 근거 입력 |
| 과정 수료 | 모든 필수 평가의 통과 확인과 수료 근거 연결 |
| 검증용 인증 | 모든 필수 과정 수료 확인과 자동 인증 |
| 결과 조회 | 평가별 상태, 수료·인증 상태, 검증 담당자의 상세 결과와 적용 기준 조회 |
| 기록 무결성 | 실패 이력 보존, 기준 고정, 중복 처리 방지, 주요 변경 사유 기록 |
| 실제 수행 비교 | 과정별 확정 평가 회차 직접 선택, 독립 수행 근거 기록, 비교 결과·정정 이력 보존 |
| 공지 | 제목·본문·게시 상태 저장, 게시한 공지만 학습자·FT에게 제공 |

사용자·역할·FT는 초기 검증 인원을 기준으로 등록한다. 조직도나 범용 권한 설정 화면을 먼저 구축하지 않는다. 학습자는 본인 기록, FT는 배정된 평가, 운영자는 담당 검증 대상의 기록을 조회한다. 역할을 겸해도 자기 실기 평가는 허용하지 않는다.

검증 데이터의 오입력을 처리하는 최소 기능은 과제 전체를 검증 대상에서 제외하고 사유를 남기는 것이다. 해당 과제의 평가·수료·인증 원본은 보존하고 결과 조회에 제외 여부를 표시한다. 제외한 과제에는 새 응시, 최종 평가 제출, 수료·인증 생성을 허용하지 않는다. 수정한 조건은 새 과제로 검증한다. 이는 정상적인 재응시와 구분하며, 평가 결과를 덮어쓰는 기능으로 구현하지 않는다.

### 후속 범위

| 원문 기능 | 이번 단계의 처리 |
| --- | --- |
| 6단계 운영조직, 상위 자격 상속, 조직 이동 | 직접 자격 배정으로 대체 |
| 계획 작성, 2~3단계 결재, 반려·회수·기간 변경 | 과제 배정 목록과 현재 상태로 축소 |
| 정책의 별도 승인 흐름, 문항 라이브러리 운영 고도화 | 필요한 기준 입력·검증·버전 고정만 구현 |
| 수동 인증 승인 | 자동 검증용 인증 한 방식만 구현 |
| Hold, 장기 Hold 효력 해제, 만료, 재인증 | 후속 운영 단계로 이동 |
| 수료증·인증서 PDF | 결과와 근거 조회 화면으로 대체 |
| 인력 CSV 미리보기·일괄 가져오기 | 초기 참여자 사전 등록으로 대체 |
| 조직별 대시보드, 과거 실적 통계, 알림함·배치 | 단순 진행 목록과 결과 조회로 축소 |
| 수료 재사용, 버전 간 동등 인정 | 동일 수강·동일 버전 안에서 평가 통과 유지까지만 지원 |
| Knox·DSCovery 등 연동, SSO 운영 연동 | 검증 환경의 계정과 학습자료 링크 사용 |
| 그룹 인증, Auditor, AI, 다국어 | 후속으로 유지 |
| 1,000명·100개 자격 규모의 성능 검증 | 확정된 파일럿 규모에 맞춰 검증 |

권한 확인, 정답 보호, 제출의 원자적 처리, 이력 보존은 위 범위 축소와 관계없이 유지한다. 실제 사용자 정보가 포함되면 그에 맞는 접근 통제와 저장 환경을 적용한다.

## 6 샘플 데이터

자격명은 Recipe Management이고 필수 과정은 Recipe 생성과 Recipe 편집이다. 아래 내용은 등록 데이터이며, Recipe를 생성하거나 편집하는 업무 시스템 연동을 요구하지 않는다.

| 과정 | 객관식 문항 | 정답 |
| --- | --- | --- |
| Recipe 생성 | Recipe 생성을 할 수 있는 직급은? | 미정 |
| Recipe 생성 | Recipe 생성을 수행하는 시스템 명은? | 미정 |
| Recipe 편집 | 하루에 편집 가능한 Recipe 수는 몇 개인가? | 미정 |
| Recipe 편집 | Recipe 편집 후 반드시 수행해야 하는 절차는 무엇인가? | 재검토 |

‘재검토’를 시스템 상태, 결재 단계, 별도 검토자의 작업 또는 실기 항목으로 해석하지 않는다. 시스템은 선택한 답과 등록된 정답을 비교한다.

이 샘플에는 선택지, 세 문항의 정답, 배점, 합격 기준과 실기 항목이 아직 없다. 해당 값이 필요한 평가 구성은 초안으로 유지하며, 필요한 입력을 채운 뒤 배정한다. 샘플 문항의 내용을 근거로 실기 항목이나 실제 회사 규칙을 자동 생성하지 않는다.

## 7 수료와 인증 근거의 데이터 구조

| 데이터 | 책임과 제약 |
| --- | --- |
| QualificationRevision | 자격명, 필수 CourseRevision 목록, 고정된 버전 |
| CourseRevision | 과정명, 학습자료, 필수 평가 구성, 고정된 기준 |
| CourseAssessment | 과정 안의 객관식 또는 실기 평가 설정. 과정 버전·평가 종류별 하나 |
| ItemRevision | 객관식 문항·선택지·정답·배점 또는 실기 항목·판정 기준 |
| QualificationAssignment | 직원에게 특정 자격 버전을 배정한 검증 과제 |
| CourseEnrollment | 과제에 포함된 특정 과정의 수강과 평가 진행 상태 |
| AssessmentAttempt | 수강·평가 종류별 응시 회차, 기준 스냅샷, 제출 결과, 실기 평가자 |
| ItemResult | 응시의 문항별 응답 또는 실기 항목별 판정과 근거 |
| Completion | 해당 수강의 필수 평가를 모두 충족한 수료 기록. 수강당 하나 |
| CompletionEvidence | 수료에 사용한 필수 평가별 합격 응시 연결 |
| Certification | 과제의 모든 필수 과정 수료로 생성한 검증용 인증. 과제당 하나 |
| CertificationEvidence | 인증에 사용한 필수 과정별 수료 연결 |
| AuditEvent | 배정, 기준 고정, FT 변경, 검증 제외 등 주요 변경의 주체·시각·사유 |
| Comparison | 과정 수강, 비교 회차·버전, 수행 관찰, 독립성, 비교 결과, 정정 원본 연결 |
| IdempotentRequest | 변경자·요청 식별자·내용 지문·반환 결과를 저장해 재전송 중복 방지 |

위 구조는 논리적인 책임을 나타낸다. DB 테이블을 만들지 않는다. 과정 JSON의 `mode`와 문항·실기 항목 배열로 CourseAssessment와 ItemRevision을 표현하고, 수료·인증의 `evidence` 배열에 명시적인 근거 연결을 저장한다. 각 응시는 불변 과정 버전 식별자를 참조하므로 적용 기준을 재현할 수 있다. 자격과 과정 사이에 새로운 업무 단계를 추가하지 않는다.

과정의 평가 구성은 `objective / practical / both`로 표현하며, 수료에는 단일 attemptId 대신 필수 평가별 합격 응시를 각각 연결한다. 과정·항목의 식별자는 해당 버전 안에서 과거 기준을 재현할 수 있도록 유지한다.

평가 제출 시 권한·상태 검사, 채점, 수료, 자격 요건 확인, 인증, 감사 기록, 중복 요청 정보를 단일 JSON 쓰기 대기열 안에서 처리한다. 검증한 새 상태를 임시 파일에 기록·동기화하고, 이전 상태 백업과 원자적 교체를 완료한 뒤 성공을 반환한다. 수강당 수료 하나·과제당 인증 하나를 서버 상태 검사와 파일 참조 검증으로 보장한다.

근거 연결은 같은 직원, 같은 수강, 배정된 기준 버전의 통과한 응시에 한정한다. 미통과 응시나 다른 직원의 결과가 수료·인증 근거로 사용되어서는 안 된다.

### 파일과 세션

Node 24·Fastify 5·TypeScript·Zod 4를 사용하며 npm workspaces로 프런트엔드·서버·공유 계약을 관리한다. 저장 파일에는 `schemaVersion`을 포함하고 서버만 접근한다. 초기화는 명령으로 명시적으로 수행하며, 파일 손상 시 시작을 중단하고 검증된 백업을 명시적으로 복구한다. 저장소별 프로세스 잠금으로 중복 서버 실행을 막는다.

로컬 계정 전환은 메모리 세션과 HttpOnly·SameSite 쿠키를 사용한다. 서버 재시작 후에는 다시 계정을 선택한다. 역할은 배열로 관리하고 모든 변경과 조회에서 본인·현재 FT·담당 운영자 관계를 검사한다. 학습자에게 정답·문항별 득점·타인 기록을 보내지 않는다.

응답과 FT 초안은 입력 후 500ms에 저장한다. 저장 실패 시 입력을 보존하며, 마지막 저장 또는 충돌 해결이 끝나기 전에는 제출하지 않는다. 변경 요청은 식별자를 갖고, 같은 식별자·같은 내용은 기존 결과를 반환하며 다른 내용은 충돌로 처리한다.

## 10 평가 기준 검증과 준비할 데이터

시스템 수용시험은 채점·수료·인증의 처리 규칙을 검증한다. 평가 기준이 실제 직무수행의 최소 요건을 구별하는지는 별도의 비교 근거가 있어야 판단할 수 있다. 현재 기존 평가 자료와 수행 비교 근거는 확보되지 않았다.

평가 기준 검증을 준비할 때 실제 문항·실기 기준을 정하고, 비교할 작업 수행 결과와 그 판정 방법을 먼저 정한다. 2026-10-16 사용자 선택에 따라 별도 검증표 방식 대신 관리의 `기준 검증`에서 과정별 기록을 저장한다. 통계 대시보드와 첨부파일 업로드는 추가하지 않는다.

- 운영자는 같은 직원·수강·기준 버전의 확정된 객관식·실기 회차를 각각 직접 선택한다.
- 관찰일, 관찰자, 작업, 실제 수행 판정 기준, 근거 요약, 선택적인 HTTP(S) 근거 URL을 기록한다. 미완성 내용은 초안으로 저장한다.
- 수행 판정은 최소 요건 충족·미충족·판정 불가다. 비교 결과는 양쪽 충족·평가만 충족·실제 수행만 충족·양쪽 미충족·비교 보류로 계산한다.
- 동일한 FT 평가의 결과를 다시 사용하거나 독립 여부가 불명확하면 비교 보류다. 수행 판정이 불가한 경우도 비교 보류다. 보류 기록은 타당성을 확인한 사례로 취급하지 않는다.
- 확정한 응시 식별자와 기준 버전은 재응시·기준 개정으로 변하지 않는다. 정정은 사유와 원본 연결을 가진 새 기록으로 남긴다.
- 제외된 과제와 정정 전 기록은 원본을 보존하고 상태를 표시하며 유효한 비교 대상에서 제외한다. 비교 기록은 평가 통과·수료·인증을 자동 변경하지 않는다.

평가 합격과 수행 근거가 일치하지 않는 사례를 모아 문항, 실기 항목, 합격 기준을 보완한다. 수정 전후의 결과는 서로 다른 기준 버전으로 구분한다. 동일한 FT 평가 결과를 그대로 비교 정답으로 사용한 결과만으로 기준의 적절성이 확인됐다고 판단하지 않는다.

| 준비할 내용 | 현재 상태 |
| --- | --- |
| 샘플 객관식 선택지와 미정인 세 문항의 정답 | 입력 필요 |
| 객관식 배점과 합격 기준 | 입력 필요 |
| 실기 항목과 항목별 판정 기준 | 입력 필요 |
| 검증 참여자, FT, 운영자 | 선정 필요 |
| 실제 평가 기준과 비교할 수행 근거 | 확보 방법 결정 필요 |
| 파일럿 규모, 기간, 평가 기준 검증의 성공 조건 | 비교 방법과 함께 결정 필요 |

위 항목은 검증에 사용할 내용과 운영 조건이다. 샘플 자격명이나 정답 문자열을 새로운 시스템 기능으로 확장하지 않는다.

## 11 구현 순서

1. 서버·JSON 저장·세션과 요청 중복·수정 충돌 처리를 연결한다.
2. 한 과정의 객관식·실기 평가, 부분 통과 유지, 재응시, 합격 근거를 연결한 수료를 구현한다.
3. 필수 과정 수료를 연결한 자동 인증과 결과 조회를 구현한다.
4. 기준 버전·배정·FT 변경·검증 제외·공지·자료 URL·문항 분류를 연결한다.
5. 과정별 실제 수행 비교, 확정, 정정 이력을 구현한다.
6. 전체 사용자 여정, 중복·동시 요청, 저장 장애·재시작·복구, 권한, 1920×900·좁은 화면을 검증하고 실행 안내와 인수인계를 갱신한다.

개발의 첫 완료 단위는 ‘혼합 과정 하나의 평가부터 수료까지’로 둔다. 조직 관리나 다단계 결재를 먼저 완성하는 원문의 구현 순서를 변경한다.

## 12 원문 대비 주요 변경

| 원문 위치 | 변경 |
| --- | --- |
| 3절 P0와 4절 범위 | 최초 취득·만료를 포함한 운영 범위에서 평가·수료·검증용 자동 인증으로 축소 |
| 5절 권한 | 검증 참여자의 기본 역할과 대상 관계 확인을 유지하고 조직 운영·권한 관리 고도화는 후속으로 분리 |

| 21–23절 시험·개발 | 혼합 과정, 부분 통과 유지, 자동 인증을 중심으로 재구성 |
