# 인증Set 명칭·자격 상태·대상자 Hold·재인증 구현 계획

작성일: 2026-10-22 · Asia/Seoul

상태: 현재 구현을 읽고 수립한 개발 계획이다. 아래 기능은 아직 구현하지 않았다. 기준 코드 `4af1b3c`, 업무 스키마8 revision173, 조직 스키마2 revision3에서 검토했다.

## 1. 리뷰 결론과 확정한 운영 결정

최초 취득은 인증Set별 평가·수료를 통해 진행하고, 재인증은 보유 자격에 연결된 별도 종합평가 절차로 분리한다. 상태는 **자격 기준 / 개인 보유 자격 / 인원별 취득 대상 여부**의 세 영역에서 각각 관리해야 한다.

사용자가 확인한 결정은 다음과 같다.

1. 자격을 구성하는 ‘과정’의 명칭을 ‘인증Set’으로 바꾼다.
2. Active / Hold / Revoke는 자격 기준과 개인 보유 자격 양쪽에 적용한다.
3. 취득 대상자 Hold는 인원 단위다. 해당 인원의 모든 자격 취득·재인증과 대상자 통계에 적용한다.
4. 재인증을 완료하면 **기존 만료일에 인증기간을 더한다.** 일찍 갱신해도 잔여 유효기간을 잃지 않는다.
5. 자격 기준의 Hold/Revoke는 신규 계획·재인증을 중단한다. 기존 확정 배정과 보유 자격의 상태는 유지한다.
6. 개인 보유 자격의 Hold·해제·Revoke는 팀 조직 관리자와 시스템 운영자가 처리한다. 세부 조직 관리자는 직접 소속 인원의 대상자 Hold만 처리한다.
7. 재인증 시작 시점의 기본값은 만료 3개월 전이다. 종합평가는 이번 MVP에서 학습자의 `종합평가 완료` 버튼으로 완료한다.
8. 만료일까지 갱신하지 않으면 보유 자격을 Revoke로 처리한다. 이후에는 인증Set별 최초 취득 절차를 다시 수행한다.

아래 버전 적용 단위, 재인증의 새 기준 선택, 짧은 인증기간 처리와 이관 방식은 이 계획의 구현 권장안이다. 코드에 이미 구현된 정책으로 보지 않는다.

| Excel 과정 표·과정 선택·과정코드 | 인증Set 표·인증Set 선택·인증Set코드 |

- 메뉴·브레드크럼·제목·버튼·입력 라벨·접근성 이름·툴팁·오류·알림·증명서·검색/필터·관리 결과·Excel·현재 사용 안내·MVP 프로세스 설명까지 적용한다.
- ‘인증 과정에서’, ‘전체 업무 과정’처럼 일반 절차를 뜻하는 단어는 문맥에 맞게 유지한다. 단순 전체 문자열 치환을 하지 않는다.
- ID, 버전 계보, 기존 응시/수료 근거, 발급 당시 사용자 입력, 과거 감사 원문은 보존한다. 사용자가 작성한 설명·문항 내용을 임의로 치환하지 않는다. 과거 시스템 알림/증명서의 구성요소 라벨은 표시 계층에서 새 명칭을 사용한다.
- 기존 `/admin/courses`, `course` 쿼리, API 경로와 `courseIds` 등 저장 키는 호환성을 유지한다. 화면 표시명과 도메인 용어 매핑을 공통화해 새 화면에서 옛 명칭이 다시 생기지 않게 한다.
- 인증Set의 기존 초안/사용 등록·운영 종료/재개 정책은 유지한다. 자격 상태를 인증Set 운영 상태에 자동 전파하지 않는다.

## 3. 세 종류의 상태와 변경 규칙

### 자격 기준의 운영 상태

권장 적용 단위는 **자격 버전**이다. 사용 등록 여부와 별도 `lifecycleStatus`로 관리한다. 사용자는 상태 변경 화면에서 자격명·버전·조직과 영향 범위를 확인한다.

| 상태 | 신규 계획·확정 | 재인증 시작·완료 | 기존 확정 배정·보유 자격 |
| --- | --- | --- | --- |
| Active · 운영 중 | 현재 팀 적용 버전이고 다른 조건 충족 시 허용 | 허용 조건을 별도로 검사 | 기존 기록으로 진행·유지 |
| Hold · 운영 보류 | 차단, 작성 중 초안 입력 보존 | 차단, 작성 중 재인증 내용 보존 | 기존 배정 진행·자동 취득 허용, 기존 보유 자격 상태 유지 |
| Revoke · 운영 폐기 | 차단 | 차단 | 기존 배정과 취득 이력 유지, 개인 자격을 자동 폐기하지 않음 |

- `draft/published`는 작성·등록 상태, Active/Hold/Revoke는 운영 상태로 각각 표시한다. 초안이 Active 기본값을 갖더라도 사용 등록 전에는 신규 계획 대상이 아니다.
- 팀 관리자/운영자가 상태와 사유를 변경한다. Hold는 같은 버전의 Active로 재개할 수 있다. Revoke 버전의 재사용은 새 버전의 검토·사용 등록과 팀 적용 버전 선택으로 처리하는 것을 권장한다.
- 자격 버전의 내용 변경은 기존처럼 새 버전으로 한다. 상태 변경은 내용 개정 없이 revision·이력으로 처리한다.
- 팀 후보 목록이나 조직 필수 목록에서 자동 제거하지 않는다. `기준 Hold로 신규 계획 불가` 등 원인을 표시한다. 등록된 버전이 바뀌어도 팀 적용 버전은 자동 변경하지 않는다.
- 보유 자격의 취득 당시 버전이 Hold/Revoke가 된 경우에도 해당 보유 자격을 자동 정지/폐기하지 않는다. 재인증에 사용할 현재 팀 적용 버전이 Active인지 확인한다. 더 새 Active 버전이 있더라도 관리자가 팀 적용 버전을 선택하기 전에는 자동 대체하지 않는다.
- 상태 변경 전에 관련 필수 지정 조직·계획 초안·기존 배정·보유 자격·진행 중 재인증 건수를 보여준다. 기존 배정 유지와 신규/재인증 차단을 확인한 후 사유와 함께 저장한다.

### 개인 보유 자격의 상태

| 상태 | 의미 | 허용되는 다음 행동 |
| --- | --- | --- |
| Active · 유효 | 자격 효력이 있고 만료 전 | 재인증 가능 기간이면 종합평가 진행 |
| Hold · 정지 | 취득 이력은 있으나 현재 효력 정지 | 이력 조회, 관리자 정지 해제 |
| Revoke · 폐기 | 만료 또는 관리자 폐기로 효력 종료 | 이력 조회, 조건 충족 시 새 취득 계획 |

- 만료 예정·재인증 가능·재인증 진행/완료는 별도 표시다. 이를 Active/Hold/Revoke와 한 상태 필드에 섞지 않는다.
- Active↔Hold에는 사유와 처리자를 기록한다. Active/Hold→Revoke는 폐기 시각과 원인(만료/관리자 처리)을 기록한다.
- Hold 해제는 만료 전만 가능하다. Revoke는 기존 인증을 Active로 되돌리지 않고 새 취득으로 연결하는 것을 권장한다.
- 개인 자격 Hold는 유효 자격/필수 충족의 분자에서 제외하되, 대상자인 인원 자체를 통계에서 제외하지 않는다.
- 개인 자격 Hold와 대상자 Hold 모두 만료 시계를 멈추거나 만료일을 연장하지 않는다. 만료하면 자동 Revoke가 적용된다.
- 폐기는 기록 삭제가 아니다. 최초 취득·인증Set 수료·평가 근거·갱신·정지·폐기 이력을 계속 조회한다.

### 인원별 취득 대상자 Hold

- 사용자에 `대상 / 대상자 Hold`를 두고 역할·계정 사용 여부와 분리한다. 처음에는 모든 기존 학습자를 대상으로 이관한다.
- Hold 중에는 새 요청·계획 생성/확정·평가 시작/답안 저장/제출·재인증 시작/완료를 차단한다. 학습자료·본인 이력은 읽을 수 있다. 이미 열린 답안의 입력은 화면에 보존하고 서버 저장 중단 이유를 안내한다.
- 기존 계획·배정·답안·수료·보유 자격은 보존한다. 대상자 Hold가 개인 보유 자격을 자동 Hold로 바꾸지는 않는다. 보유 효력 정지가 필요하면 별도 개인 자격 상태 변경을 수행한다.
- 수동 해제 후 기존 진행을 재개한다. 그동안의 만료·기준 변경·소속 변경은 다시 검사한다. 기한이 지난 자격을 해제만으로 되살리지 않는다.
- 같은 Lv1 내 소속 이동 시 대상자 Hold는 인원에 유지한다. 관리 권한은 새 실제 소속 기준으로 다시 계산한다. 기존 세부 관리자 지정 해제 규칙은 유지한다.

## 4. 권한과 대상자 화면

| 기능 | 시스템 운영자 | 팀 조직 관리자 | 세부 조직 관리자 | 학습자 |
| --- | --- | --- | --- | --- |
| 자격 기준 상태·재인증 정책 설정 | 선택 Lv1 | 자기 Lv1 | 불가 | 불가 |
| 개인 보유 자격 Hold/해제/Revoke | 선택 Lv1 인원 | 자기 Lv1 인원 | 불가 | 불가 |
| 대상자 Hold/해제 | 선택 Lv1 인원 | 자기 Lv1 인원 | 직접 소속 조직의 인원만 | 불가 |
| 종합평가 완료 | 학습자 역할의 본인 | 학습자 역할의 본인 | 학습자 역할의 본인 | 본인만 |

- 세부 관리자에게 `인증 대상자 관리` 메뉴만 추가한다. 기존 조직별 자격 설정과 함께 사용할 수 있으나 계획 요청·기준 편집·다른 사람의 답안·개인 자격 폐기 권한은 확대하지 않는다.
- 대상자 목록은 이름·소속·대상 여부·변경일·사유·다음 행동으로 구성한다. 검색과 대상/Hold 필터, 체크박스 일괄 선택 및 별도 선택 목록을 제공한다.
- 상태 변경 창에서 대상 인원과 중단되는 진행 건수, 통계 제외와 보유 자격 효력 유지의 의미를 보여준다. 사유 입력·revision 확인 후 선택 집합을 원자적으로 저장한다.
- 관리자 해제/소속 이동/다른 창 수정 이후의 요청은 서버가 현재 권한으로 재검사한다. 세부 관리자의 API는 해당 인원의 최소 요약만 반환한다.
- `fullManager`에 세부 관리자를 추가하지 않는다. `manageEligibility`, `manageCredentialStatus`, `manageQualificationLifecycle` 등 기능별 권한을 서버와 화면에서 함께 사용한다.

## 5. 재인증 정책과 달력 계산

자격 개별 편집과 기준 일괄 관리에 `재인증 시작: 만료 N개월 전`을 추가한다. 신규 기간제 자격의 기본값은 **3개월**이다. 만료 알림 일수와 서로 다른 설정으로 표시한다.

- 기존처럼 Asia/Seoul 날짜를 기준으로 계산하고, 개월 계산 결과에 해당 일이 없으면 그 달의 마지막 날로 보정한다. 3개월을 90일로 치환하지 않는다.
- 만료일까지 유효하고 다음 날 00:00 KST에 폐기 효력이 발생한다.
- 재인증 시작일은 `만료일 - 설정 개월 수`다. 인증기간이 설정 개월 수보다 짧으면 해당 유효기간 시작일보다 이르게 열지 않는다. 화면에 보정된 실제 시작일을 표시한다.
- 한 유효기간의 재인증은 한 번만 완료한다. 새 유효기간이 시작되기 전에는 그 다음 주기를 또 갱신할 수 없다. 짧은 인증기간과 기본3개월 조합에서 반복 클릭으로 유효기간이 무제한 늘어나는 것을 막는다.
- 무기한은 자동 만료·주기 재인증을 제공하지 않는다. 기간 미정은 신규 사용 등록을 계속 차단한다.
- 이미 발급한 기간과 재인증 시작 정책은 발급 당시 스냅샷으로 유지한다. 자격 정책 개정이 기존 만료일/진입 가능일을 소급 변경하지 않는다.
- 새 갱신에 적용할 기준은 같은 자격 계보의 **현재 팀 적용 Active 게시 버전**을 권장한다. 이 버전의 인증기간을 기존 만료일에 더한다. 시작 화면에 취득 당시 버전과 갱신 적용 버전·기간 차이를 표시하고 고정한다.
- 재인증 중 팀 적용 버전/정책이 바뀌면 완료를 차단하고 재확인을 요구한다. 이전 초안은 이력으로 보존하고 새 적용 기준으로 다시 시작한다. 자동으로 다른 기준에 합격한 것으로 처리하지 않는다.
- 현재 소속 조직 필수 목록에서 빠졌더라도 보유 자격과 팀 적용 기준이 유효하면 재인증할 수 있도록 권장한다. 팀 후보 목록에 운영 가능한 기준이 없으면 관리자 확인 사유를 표시한다. 신규 취득/재취득의 필수 자격·관리자 요청 규칙은 별도로 유지한다.

예: 기존 만료일이 2029-10-22, 시작 설정3개월, 갱신 적용 인증기간36개월이면 재인증 가능일은 2029-07-22다. 2029-08-01에 완료해도 새 만료일은 2032-10-22다. 실제 갱신 완료일은 2029-08-01, 다음 유효기간 시작일은 2029-10-23으로 각각 기록한다. 최초 취득일은 바꾸지 않는다.

## 6. 학습자 재인증·폐기 후 재취득 UX

### 재인증

`홈/보유 자격 → 인증서·자격 이력 → 재인증 안내 → 종합평가 완료 → 갱신 결과`로 연결한다. 인증Set별 개인 계획을 새로 만들거나 과거 수료를 다시 채우지 않는다.

1. 홈과 보유 자격에 현재 상태, 만료일, 재인증 시작일, `재인증 가능`/`재인증 진행 중`을 표시한다.
2. 대상자 Hold가 아니고 개인 자격 Active·기간 내·운영 가능한 적용 기준이 있으면 `재인증 시작`을 제공한다. 새 계획 수립 요청은 필요하지 않다.
3. 안내 화면에서 현재 만료일, 적용 자격 버전/기간, 완료 시 새 만료일과 종합평가 방식을 확인한다.
4. 이번 MVP는 `종합평가 완료` 버튼과 최종 확인으로 처리한다. 실제 문항·점수·합격 판정을 만들지 않는다. 화면과 갱신 근거에는 **MVP 완료 버튼으로 처리**임을 표시한다.
5. 완료 요청에서 본인·대상자 상태·개인 자격 상태·기준 상태/버전·주기·만료·revision을 다시 검사한다. 새 기간·갱신 이력·알림을 한 번에 저장한다.
6. 결과 화면에는 갱신 완료일·이전/새 만료일·다음 재인증 가능일과 인증서 이동을 제공한다. 조회/새로고침으로 갱신을 다시 생성하지 않는다.

인증서에는 최초 취득 근거와 갱신 근거를 구분한다. 처음 취득한 인증Set 수료를 새 자격 버전의 인증Set 수료로 바꾸지 않는다. 현재 상태와 원본 발급 이력도 함께 보여준다.

### 만료·자동 폐기

- 만료일까지 완료되지 않은 재인증은 `기간 종료`로 닫고 개인 자격을 Revoke로 변경한다. 진행 중 화면이 열려 있어도 만료 후 완료는 거부한다.
- 서버 시작 시·주기 처리·관련 조회/쓰기 시 공통 달력 판정을 사용한다. 1분 타이머 사이 또는 서버 중단 구간이 있어도 만료 이후를 유효하게 표시하지 않는다.
- 이벤트에 실제 만료 효력 시각과 서버가 이를 기록한 시각을 따로 저장한다. 재시작 시 누락 폐기를 보충하고 같은 기간의 폐기를 중복 기록하지 않는다.
- 자동 처리 저장이 실패하면 만료 판정에 근거해 갱신을 차단하고 오류를 기록한다. 재시도 때 이력·상태를 일관되게 확정한다.

### 재취득

- 폐기 이력에서 `다시 취득하기`를 제공하되 현재 조직의 필수 자격·Active 팀 기준·대상자 상태를 확인한다. 조건에 없으면 구체적인 관리자 확인 사유를 보여준다.
- 기존 요청을 무기한 재사용하지 않고 **재취득용 관리자 요청 → 새 개인 계획 → 새 배정·인증Set 수강 → 각 필수 평가 → 새 자격 취득**으로 진행한다.
- 과거 수료·답안·통과를 새 배정으로 자동 복사하지 않는다. 새 취득 자격은 새 발급번호를 갖고 이전 Revoke 인증과 연결한다.
- 기존 계획/배정을 찾는 로직을 취득 회차 기준으로 바꾼다. 이전 완료 계획 때문에 새 요청이 완료로 집계되거나 새 계획이 차단되는 문제를 막는다.
- 같은 인원·자격 계보에 진행 가능한 취득 회차는 하나만 허용한다. 종합평가 재인증과 재취득이 동시에 생기지 않게 한다.

## 7. 이력·알림·통계

### 날짜 이력

- 취득, 기준/상태 변경, 재인증 시작, 갱신 완료, 정지, 정지 해제, 관리자 폐기, 만료 폐기, 재취득 연결을 사건별로 남긴다.
- 각 사건에 ID, 대상과 버전/회차, 실행자, 실제 처리 시각, 효력 발생 시각, 전후 상태/기간, 사유, 당시 조직, 요청 식별자를 보관한다. 이력은 덮어쓰지 않고 오류 정정도 새 사건으로 남긴다.
- 저장 시각은 UTC ISO, 사용자 표시는 Asia/Seoul이다. 모든 사건에 새로 만든 하나의 updatedAt만 사용하는 방식은 피한다.
- 기준 운영 이력, 인원 대상자 Hold 이력, 보유 자격 이력을 구분해 표시한다. 원본 증명서의 취득일·발급번호·당시 표기는 유지한다.

### 알림

- 재인증 시작, 기존 만료 예고, 갱신 완료, 정지/해제, 폐기 알림을 제공한다. 기존 만료 알림은 현재 주기의 실제 만료일에 연결한다.
- 중복 키에 보유 자격ID·유효기간 회차·이벤트 종류·시점을 포함한다. 갱신 뒤 이전 주기의 알림을 현재 미완료 업무로 노출하지 않는다.
- 대상자 Hold 중 계획/재인증 독촉은 중단한다. 상태·폐기 이력은 남기고 해제 시 현재 필요한 안내만 제공한다.
- 자격 기준 Hold/Revoke로 갱신이 막힌 경우 담당 관리자와 학습자에게 원인을 표시한다. 기준을 다시 Active로 바꾸어도 이미 발생한 개인 자격 폐기는 취소되지 않는다.

### 통계 규칙

- 현재 대상자 통계는 학습자 역할·관리 범위·현재 대상 여부를 공통 서버 함수로 판정한다. 대상자 Hold는 관련 분모와 분자에서 함께 제외한다.
- 인원 수와 인원×필수 자격 수를 구분한다. 자격 충족은 같은 계보의 개인 자격이 Active이면서 현재 유효한 경우만 인정한다. 갱신 회차를 별도 보유 자격 수로 세지 않는다.
- `Hold 제외 N명`을 별도 표시하고 관리 목록/이력에서는 계속 찾을 수 있게 한다. ‘등록 사용자’ 같은 원본 인원 관리 건수는 취득 대상자 통계와 구분한다.
- 자격 기준 Hold/Revoke로 생긴 미충족은 통계에서 몰래 제외하지 않고 `운영 기준 확인 필요`로 구분한다. 필수 기준 미설정도 100% 충족으로 처리하지 않는다.
- 분모가0이면 `대상 없음`으로 표시한다. 과거 시점 통계는 현재 Hold 상태를 소급 적용하지 않도록 상태 이력의 효력 시각을 사용한다.
- 기존 홈·대상자/계획·결과·유효 보유 자격 집계부터 새 규칙을 적용한다. 별도의 대형 통계 대시보드 제작은 이번 범위가 아니다.

## 8. 저장 모델·API·Excel

업무 JSON을 **스키마9**로 명시적으로 이관하고 조직 마스터는 스키마2를 유지한다. 공통 쓰기 대기열·원자적 교체·백업·revision·중복 요청 방지를 재사용한다.

| 모델 | 주요 추가 내용 |
| --- | --- |
| 자격 버전 | 운영 상태·상태 revision/이력, 재인증 시작 개월 수, 기준 정책 버전 |
| 사용자 | 취득 대상 여부·revision, Hold/해제 사유·사건 연결 |
| 기존 인증 | 안정적인 발급ID·최초 취득 근거 유지, 현재 상태·revision·현재 유효기간 요약 |
| 인증 유효기간 이력 | 최초/갱신 구분, 시작·종료·기준일, 실제 갱신일, 적용 자격/정책 스냅샷, 이전 기간 연결 |
| 재인증 | 인증ID·대상 회차·선택 기준, 시작/완료/기간 종료 시각, `mvp_completion` 처리 방식과 근거 |
| 취득 회차 | 최초/재취득 구분, 이전 폐기 인증 연결, 요청·계획·배정과 완료/종료 상태 |
| 상태 사건 | 기준/대상자/보유 자격 구분, 실행자·효력/기록 시각·사유·전후 값 |

- 기존 인증의 `date`, 최초 수료 근거를 최신 갱신 값으로 덮어쓰지 않는다. 인증서 요약의 현재 기간은 유효기간 이력에서 산출한다.
- 연속된 갱신 기간과 아직 시작하지 않은 다음 기간을 구분한다. 현재 효력과 다음 재인증 가능 주기를 함께 계산하는 단일 도메인 함수를 둔다.
- 초기 취득의 ‘배정당 최초 인증 1건’ 검증은 유지한다. 갱신 근거는 해당 인증의 별도 기간/종합평가로 검증하여 가짜 인증Set 수료를 만들지 않는다.
- 과거 참조의 무결성과 현재 신규 운영 가능 여부를 분리한다. Hold/Revoke 기준이나 폐기된 개인 자격이 존재한다는 이유로 서버 시작·이력 조회·복구 검증을 실패시키지 않는다.
- 요청 재시도는 현재 접근 권한 확인 후 최초 성공 결과를 반환한다. 새로운 요청에만 최신 상태/기간 조건을 적용한다. 재전송이 이미 완료한 갱신을 또 실행하지 않게 한다.

### API 권장안

| 인터페이스 | 역할 |
| --- | --- |
| `GET /api/qualifications/:id/lifecycle-impact` | 기준 상태 변경의 대상·영향·revision 확인 |
| `POST /api/qualifications/:id/lifecycle` | 기준 Active/Hold/Revoke 변경 |
| `GET /api/certification-targets` | 권한 범위 내 대상자/Hold 목록 |
| `PUT /api/certification-targets/eligibility` | 선택 인원 Hold/해제, 집합 단위 검증·저장 |
| `GET /api/certifications/:id/history` | 현재 상태·기간·취득/변경/갱신 이력 |
| `POST /api/certifications/:id/status` | 팀 관리자/운영자의 개인 자격 상태 변경 |
| `POST /api/certifications/:id/renewals` | 본인의 기간 내 재인증 시작/기존 초안 반환 |
| `POST /api/renewals/:id/complete` | MVP 종합평가 완료·기간 연장·이력/알림 저장 |

기존 계획 요청·확정·응시/답안/제출·Workspace·필수 자격 API에도 대상자 상태와 새 취득 회차를 반영한다. 기존 인증서 URL은 유지하고 필요한 경우 주기 쿼리로 과거 발급 이력을 조회한다.

### Excel과 기준 일괄 관리

- 사용자 양식 v4: 인증Set 명칭과 자격 메타정보의 `재인증 시작(만료 전 개월)`을 추가한다. 웹 개별/일괄 편집도 같은 검증 함수를 사용한다.
- 자격 기준 운영 상태는 내보내기에서 참고용으로 표시한다. Excel 재가져오기만으로 기존 기준을 Hold/Revoke/재개하지 않고 명시적 상태 변경 화면에서 처리하도록 권장한다.
- 기존 v3 파일은 호환 읽기를 제공한다. 신규 기준의 빠진 재인증 값은 기본3개월 적용 사실을 미리보기에서 보여준다. 기존 기준 개정은 기존 정책을 보존하고, 값이 없다는 이유로 무변경 파일에 새 버전을 만들지 않는다.
- v1/v2의 폐지된 주관식·관찰 실기 차단은 유지한다. 복구 초안의 형식 버전을 검사하고 기존 작성 내용의 정책을 조용히 바꾸지 않는다.
- 이름 있는 표·추가 선택지·코드/ID 연결·왕복 순서·정답 변환·부분 저장/게시·무변경 재가져오기를 회귀 검증한다.

## 9. 기존 데이터 이관·초기화 호환

1. 적용 직전 상태·해시·인증/기간/참조를 미리보기로 확인한다. 서버를 중지하고 업무·조직 영구 사전 백업을 만든다.
2. 자격 버전은 Active, 인원은 취득 대상으로 이관한다. 기존 기간제 기준에는 사용자 지정 기본3개월을 명시적 이관 값으로 기록한다.
3. 기존 유효/무기한 인증은 Active와 최초 기간/취득 사건으로, 이미 만료된 인증은 Revoke와 실제 만료 효력 시각·이관 처리 시각으로 변환한다. 기존 기간 미정 인증은 자동 무기한으로 바꾸지 않고 `Hold · 유효기간 확인 필요`로 보존하는 것을 권장한다. 미정 기록은 일반 정지 해제만으로 유효하게 만들지 않는다. 팀 관리자/운영자가 근거 있는 기간 정책을 확인·정정하면 기존 취득일로 최초 만료를 다시 계산하고 정정 근거·처리일을 기록한다. 확인할 수 없으면 새 취득 절차가 필요하다.
4. 과거 취득/수료/평가의 실제 시각과 ID는 그대로 쓴다. 알 수 없는 상태 변경 과거 시각을 만들어 넣지 않는다. 확보한 이관 정보는 출처를 구분한다.
5. 기존 계획·배정은 최초 취득 회차에 연결한다. 내용을 수정하거나 완료 처리하지 않는다. 현재 개발 데이터는 인증0건이므로 임의 인증/갱신을 생성하지 않는다.
6. 후보 상태를 모두 검증한 뒤 업무 JSON만 원자적으로 교체한다. 조직 JSON은 쓰지 않으며 해시가 같아야 한다. 재실행은 완료 표식으로 무변경 처리한다. 정상 시작에서 자동 이관하지 않는다.
7. 테스트 진행 초기화는 새 인증 기간·재인증·개인 자격 상태 이력과 관련 알림도 진행 대상으로 명시한다. 자격 기준 운영 상태/정책·인원 대상자 Hold/이력·조직/역할은 보존한다.
8. 재취득이 여러 번인 인원은 초기화 시 과거 종료 회차를 모두 다시 활성화하지 않는다. 최신 재시험 회차만 활성 대상으로 남기고, 초기화로 제거된 인증과의 연결은 초기화 이력으로 정리한다. 고아 참조·동시 중복 취득을 검증한다.

이번 계획 작업에서는 코드·실제 업무/조직 JSON을 변경하지 않았다. 구현 시에도 기존 기록을 초기화하는 전환을 기본으로 하지 않는다.

## 11. 프로세스 검증에서 함께 확인할 사항

- 상태를 같은 ‘Hold’ 한 칸으로 보여주면 기준 운영 보류·개인 효력 정지·대상 인원 제외를 혼동한다. 영역 이름과 영향 문구를 항상 함께 표시한다.
- 재인증은 이번에 실제 능력을 재평가하지 않는다. 모의 완료 버튼이라는 근거를 인증 이력까지 유지하고, 향후 실제 종합평가 엔진으로 바꿀 수 있도록 처리 방식/정책 버전을 저장한다.
- 기준 Hold로 갱신이 막힌 동안에도 개인 만료일은 흐른다. 관리자에게 영향 인원과 다가오는 만료를 표시해 운영 결정을 할 수 있게 한다. 임의 유예/자동 연장은 이번 정책에 없다.
- 갱신은 기존 취득의 유효기간을 이어 가는 행동이고, 폐기 후 취득은 새 증거를 만드는 행동이다. 두 화면과 기록을 분리해 과거 평가만으로 새 자격이 발급되지 않게 한다.
- 현재 범위는 자격 상태·재인증 프로세스 검증이다. 실제 종합평가 문항/합격 기준·자동 승인·추가 결재·실제 직무 수행 판정은 별도 설계가 필요하다.
